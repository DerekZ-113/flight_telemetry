# Flight Telemetry System — Software Design Description

> **Document ID:** FTS-DD-001

> **Status:** Draft

## 1. Purpose and Scope

This document records the architecture of the Flight Telemetry System and the reasoning behind its design decisions. It exists so that a reviewer can see why the system is shaped this way without reading the source, and so that later decisions are made against a written baseline rather than memory.

It is not an API reference, a build guide, or a tutorial. Interfaces are documented in the headers; build and run instructions are in the README. Where this document and the code disagree, the code is wrong or this document is stale, and either way the disagreement is a defect to record.

---

## 2. Software Level: DAL C

This project assumes Design Assurance Level C under DO-178C. DAL C corresponds to a *major* failure condition: a failure that significantly reduces safety margins or significantly increases crew workload, but from which a safe landing remains possible. A telemetry display that shows wrong altitude or attitude fits that class. It could mislead a pilot and raise workload; on its own it does not cause loss of the aircraft, because certified primary instruments remain.

The practical consequence is in DO-178C Table A-5 (verification of verification process outputs). At DAL C the structural coverage objectives are statement coverage and decision coverage. Modified Condition/Decision Coverage is required only at DAL A. This is the formal basis for the branch coverage thresholds in FTS-TP-001 Section 6 and for MC/DC being out of scope there. The thresholds are not arbitrary targets; they are the DAL C ceiling.

DAL C is an assumption for a development system, not a certification claim. No safety assessment (ARP4761) has been performed, and none is planned. The level was chosen because it is the lowest level at which structural coverage is required, which makes it the lowest level at which the coverage tooling in this project has a reason to exist.

Two further limits apply to every verification claim in this document set. **No independent verification.** Nothing in this project was reviewed or tested by a party independent of the development; the requirements, the code, the tests, and the verification results were all produced and checked within the same development activity. **No tool qualification.** No tool was qualified under DO-330. The coverage figures and the static-analysis result in FTS-VR-001 are taken as reported by gcov, lcov, and cppcheck; a certification project would qualify at least those verification tools, whose output is credited without further checking, at TQL-5 before relying on them.

## 3. DataSource Abstraction

Every frame enters the system through the `DataSource` interface (`src/data_source.h`): one pure virtual method, `read_frame()`, returning a `TelemetryFrame`. The processing engine holds a reference to the base class and never learns the concrete type. The factory in `main.cpp` is the only place that does.

**Raw-only contract.** A source fills raw sensor fields only: pressure, temperature, accelerometer, gyroscope, GPS position and speed, and channel status. Every computed field (barometric altitude, pitch, roll, fused altitude, vertical speed) is written by the pipeline. A source that computed its own altitude would be a source and a pipeline at once, and replay could no longer prove that the pipeline reproduces live behavior.

**Why.** REQ-LOG-004 requires replay to use the same processing pipeline as live mode, differing only in data source. That is only meaningful if the pipeline is a pure function of the raw frames it receives. The abstraction makes the source the single variable.

**Planned implementations.**

| Source | Status | Role |
|---|---|---|
| `SimulatedSource` | Built | Seeded Gaussian noise around a stationary Foster City fix. Deterministic per seed on a given toolchain. |
| `LiveSensorSource` | Built | BMP280 (or BME280) and MPU6050 over one I2C bus; GPS fields zero and never fresh until the NEO-6M driver exists. Selected by `telemetry --live`. TC-014. |
| `LogReplaySource` | Built | Reads the binary log written by the logger, strips computed fields and status, feeds the raw frames back through the same pipeline. Selected by `telemetry --replay <file>`. TC-004. |
| `ADSBSource` | Sprint 2 | Real aircraft state vectors from OpenSky, presented as if they were the vehicle's own sensors. IMU channel permanently DEGRADED because ADS-B carries no attitude. See Section 11. |

**Live sensor source.** `LiveSensorSource` (`src/drivers/live_sensor_source.h`) owns the bus and the two drivers, in that order, and a reference to the monotonic clock. Each `read_frame()` stamps the frame (Section 10), reads the barometer and the IMU, leaves the GPS fields zero with `gps_read_ok` false, and sets every status NOMINAL: raw fields, `read_ok`, and nothing else, the same contract as the simulator, so the detector and the processor cannot tell the two apart. A failed read holds the channel's fields at the last good values and clears that channel's `read_ok`, which is exactly what `FaultInjectingSource::fail_reads` produces, so a pulled wire and the injector make the same frames and the freshness and timeout tests already cover the consequences; before the first good read the fields are the zeros of a value-initialized frame. A barometer whose data registers still hold the reset value (no conversion complete yet) counts as not read. Both drivers are initialized in the constructor and a failure leaves `ok()` false with every failed chip named and the cause; `main` prints that line and exits, because a chip absent or misidentified at startup is a wiring or configuration error, not an in-flight fault (a lazy re-initialization that would let a channel come back belongs with the faults work). The bus and the addresses are `sensors.i2c_device`, `sensors.barometer.address` and `sensors.imu.address` in the configuration file (REQ-CFG-001), and the IMU's sample rate `sensors.imu.sample_rate_hz`; the addresses are provisional (Section 12).

**The I2C bus seam.** The drivers never call the operating system. They call `I2cBus::write_register()` and `I2cBus::read_registers()` (`src/drivers/i2c_bus.h`), one object per bus addressed per transaction, the way the scheduler calls `Clock` and the pipeline calls `DataSource`. `LinuxI2cBus` is the only code that knows what a device file is: it opens `/dev/i2c-1` once, issues `ioctl(I2C_SLAVE, address)` before every transaction because two drivers share the descriptor and alternate addresses every cycle, then writes the register address and reads or writes the bytes. The descriptor is held under RAII, with copying deleted so no two objects can close it. Transactions report false and keep `errno`; nothing throws, because a failed read is an expected event that REQ-FAULT-001 budgets for, not an error. Tests drive the drivers through a fake bus (`tests/unit/fake_i2c_bus.h`) holding a 256-byte register file per address, so each driver's register protocol and arithmetic are proven on a machine with no bus; the fake fails transactions per register, so every branch of a driver's `init()` is reachable. The Linux implementation sits inside the second platform split in the codebase (Section 10); on macOS the class compiles to a stub that reports ENOTSUP, so one source list builds everywhere. A register read is two transactions with a stop between them (write the address, read the bytes); both datasheets permit the stop, and a bus that needed a repeated start would change one function to `ioctl(I2C_RDWR)` with nothing above it.

**Barometer driver.** `Bmp280` (`src/drivers/bmp280.h`) is named for the chip the documents assume and accepts both Bosch identities, 0x58 (BMP280) and 0x60 (BME280), because the BME280's pressure and temperature paths are register-compatible (Section 12); `chip_id()` reports which answered, and anything else is refused with the byte in the message. `init()` reads the 24 calibration bytes at 0x88 (little-endian words, `dig_T1` and `dig_P1` unsigned), then writes `ctrl_meas` = 0x00 (sleep), `config` = 0x00 (0.5 ms standby, IIR filter off), `ctrl_meas` = 0x2F (temperature ×1, pressure ×4, normal mode): sleep first because a `config` written in normal mode may be ignored and a chip left running by a previous process is in normal mode. The settings give about 70 to 83 conversions per second, so a 50 Hz loop never reads one twice, and the IIR filter stays off because the pipeline owns filtering: the Kalman filter is the filter of record and the noise run must measure the sensor, not the chip's smoother. `read()` bursts the six data registers at 0xF7, because the chip shadows them together and byte-wise reads could mix two conversions, assembles two 20-bit fields (high byte first, the opposite order from the calibration), returns nullopt if either is still the reset value 0x80000, and runs the datasheet's integer compensation: `t_fine` from the temperature feeds the pressure, which is why REQ-SENS-002 reads the two together. The compensation is the datasheet's int32 temperature and int64 pressure code transliterated, with the signed left shifts turned into multiplications by the same power of two (shifting a negative value left is undefined behavior in C++17, and the datasheet's own example does it); 64 bits are not optional, because `var1 × var1 × dig_P6` overflows int32 once |var1| exceeds 17,515, which with the example's trimming set is any temperature outside 21.6 to 28.4 °C. The worked example on page 23 of datasheet revision 1.14 is reproduced to the count (TC-012).

**MPU6050 driver.** `Mpu6050` (`src/drivers/mpu6050.h`) checks WHO_AM_I (0x68; the MPU-6500's 0x70 and clone values are refused), then writes five registers: `PWR_MGMT_1` = 0x01 (wake, clock from the X gyroscope's PLL, which the register map recommends over the internal oscillator), `SMPLRT_DIV` for the configured rate (default 100 Hz, twice the loop rate so every poll sees a new sample; one divider serves both sensors, which is REQ-SENS-004), `CONFIG` = 4 (a 20 Hz low-pass filter, below the 25 Hz Nyquist limit of a 50 Hz consumer, 8 ms of delay against a one-second filter time constant), `GYRO_CONFIG` ±250 deg/s and `ACCEL_CONFIG` ±2 g (the finest resolutions; ±2 g is also what FAULT-010's limit assumes). `read()` bursts the fourteen output registers at once, because the chip latches them together and byte-wise reads could mix two samples, assembles each big-endian pair as unsigned and casts to `int16_t` for the sign, and scales by 16384 LSB/g × 9.81 and 131 LSB per deg/s. The chip-to-body axis mapping is the identity, in one place, so a sign the hardware tilt test disagrees with is a one-line change (Section 6). A rate the 8-bit divider cannot produce exactly is refused rather than rounded, which is why REQ-SENS-003's floor is 4 Hz.

**The Python side.** `pipeline/log_reader.py` is the Python twin of `LogReader`: it reads a file through `frame_format`, keeps every complete record and counts a torn tail the way the C++ reader stops on one, refuses an unknown tag, and reads a rotated sequence as one run only when the indices are consecutive, the timestamps increase across the boundary, and the step across it is under a second. A leftover file from an earlier run restarts at 0 and is refused; a leftover from an aborted capture of the same length would join seamlessly (same start, same rotation boundary, same rate), so the reader's summary also prints the frame total and warns when file times are out of order, and the capture procedure clears `logs/` first. It derives a numpy layout from the same struct format string and asserts every field offset against `struct` at import, so the array can never misread the compiler's padding. `analysis/noise_profile.py` consumes it (Section 5, FTS-NP-001). Both are standard-library at import, so the reader's summary runs on the Pi without the venv. `tests/integration/` holds the pytest suite; one simulated session per run, in a temporary directory, serves every test.

**Configuration (REQ-CFG-001, REQ-CFG-002, REQ-CFG-003).** One YAML file, `config/telemetry_config.yaml` or the path given by `--config`, is the standing configuration: 36 keys, every tunable the SRD calls configurable, grouped as their consumers take them (`timing`, `sensors`, `fault`, `processing`, `logging`, `transport`, `simulation`). It is a parameter data item in DO-178C's sense (2.5.1): a file with its own structure and limits, verified with the executable rather than patched into it. `main` loads it once at startup through `src/config/telemetry_config.cpp`, the one translation unit that includes yaml-cpp (0.9.0, fetched and pinned like Google Test), which turns the document into typed structs and checks every value's type and range as it goes: parse, don't validate. yaml-cpp is the document parser only; the scalar rules are the project's and the file's header states them (a whole number is decimal digits or `0x` hex, so `010` is refused rather than read as octal; a number is anything `strtod` reads in full that is finite; a switch is exactly `true` or `false`; text is non-empty), because a value two readers read differently has no place in a file validated by name. Every problem the file has is reported in one pass, in the file's order, under its dotted key (`fault.stuck_count: must be at least 2 (got 1)`), which is REQ-CFG-002's "each"; an unknown or duplicate key is a problem too, so a misspelled key cannot silently leave a value at another setting; three rules run between sections (the UART timeout against the GPS period, the IMU rate against the processing rate, the UDP host through `inet_pton` whether or not that transport is enabled). Nothing is built before the file passes, and nothing re-reads it: the loop reads values, never the file, which is why a value is validated at startup and never mid-flight. The values reach their consumers by constructor, by value: the module-owned structs (`FaultDetectorConfig`, `ProcessorConfig`, `SimulationNoise`) and plain arguments for the rest. No module includes the configuration header and no global holds a value, so every test can hand a module any value and the composition root is the one place that knows a file exists. The defaults compiled into those structs equal the shipped file and are the unit tests' baseline, never the binary's fallback: a missing file is refused, and `ConfigTest.ShippedFileEqualsDefaults` fails the build if the two drift apart. Flags choose the run (`--live`, `--replay`, `--cycles`) and enable a transport for one run with its own address (`--zmq`, `--udp`); nothing else on the command line overrides a key. Not keys, each for a reason: the run length (a property of the run), the ZeroMQ high-water mark and linger (Section 12), the record's prefixes and file names (its naming contract), the ISA constants, register maps and chip identities (facts, not tuning), and the simulator's base scenario (a scenario, not noise). The configuration a session ran with is recorded beside its log (Section 9).

## 4. Processing Pipeline Order

```
DataSource  →  FaultDetector  →  TelemetryProcessor  →  Logger / ZeroMQ / UDP / Display
 raw + read_ok     raw + status        raw + computed
```

The fault detector sits before the processor. This is the most important ordering decision in the system.

The detector takes its notion of time from `frame.timestamp_ms`, never from a wall clock. That keeps it a pure function of the frame sequence: a replayed log produces the same faults at the same frames (REQ-LOG-003), and tests advance time by handing in frames with later timestamps. It also fixes the strictness of the timeout comparison. With frames every 20 ms and the last success at t−20, elapsed `> 500` declares the fault 500 ms after the first failed read; `>=` would declare it at 480 ms, which TC-002 treats as a false alarm on a single transient error.

Both filters in `TelemetryProcessor` gate on `ChannelStatus` and on `read_ok`: a DEGRADED channel contributes nothing, and a NOMINAL channel contributes only on a cycle that produced a reading (REQ-PROC-006, Section 5). That gate only protects the filters if status is correct *before* the frame reaches them. A stuck or out-of-range reading that arrives marked NOMINAL enters the Kalman update or the complementary filter and corrupts state that persists across every subsequent frame. Detecting the fault afterward does not undo that. So detection must run first, on the raw frame, and the processor must trust the status it is handed.

The processor itself is a class rather than a free function because both filters carry state between frames. It is passed by non-const reference through the loop and created once, outside it, so the same instance sees every frame in order.

## 5. Kalman Filter Design

`KalmanFilter1D` (`src/processing/kalman_filter.h`) fuses barometric and GPS altitude (REQ-PROC-003).

**Why 1D, not an extended Kalman filter.** One spatial axis, a linear motion model, and direct measurements of the state mean the standard linear filter is exact. An EKF linearizes a nonlinear model; there is nothing here to linearize. Choosing the simplest filter that is correct keeps every line explainable, which is a project goal in its own right.

**Why two states.** Altitude alone cannot be extrapolated between measurements. Adding vertical velocity gives the predict step something to integrate, and the covariance coupling between the two states lets an altitude-only measurement correct velocity. Vertical speed is therefore estimated without a vertical speed sensor.

**Constant-velocity model and its limits.** The predict step assumes velocity does not change between frames. Process noise Q, built from a single acceleration variance, admits that it does. The model lags under sustained acceleration (rotation, flare, strong thermals). A larger Q shortens the lag at the cost of smoothing. A third state (acceleration) or an IMU-driven predict step would address this and is out of scope.

**Tuning.** Of the filter's five constants (the `processing` keys of the configuration file, the initial altitude variance derived from the barometric one), two are measured by the noise characterization (FTS-NP-001, REQ-PROC-004): the barometric measurement variance, taken as the white part of the barometric altitude noise on a stationary capture (the one-sample Allan deviation squared, which a slow pressure trend cannot inflate the way the plain variance would), and the initial altitude variance, which equals it because the filter is born from one barometric sample. Two are retained as documented tuning choices, because no bench capture can show them: the process noise is the vehicle's unmodelled vertical acceleration (σ_a = 1 m/s²; with a barometric variance near 0.07 m² the filter then sees 90% of a 1 m/s climb after about 1.4 s, where a Q taken from the accelerometer's own electronic noise, as once planned, would take almost 10 s), and the GPS variance stays the receiver's datasheet figure (25 m²) until REQ-SENS-005 delivers a GPS to measure. The fifth, the initial velocity variance, is the cause of the startup transient of about 0.7 m/s in vertical speed on a stationary board: the prior velocity uncertainty random-walks until the altitude data pins it, a smaller barometric variance does not remove it, and a value of 0.01 (m/s)² would cut the peak to about 0.17 m/s at the cost of seeing a vehicle already climbing at birth about a second later. It is chosen by replaying the capture through candidate values under a rule written before the data (FTS-NP-001 Section 3). Until the capture of 2026-10-13 is analyzed the placeholders stand (3 m² barometric, 25 m² GPS, 1 (m/s)², 1 (m/s²)²) in `config/telemetry_config.yaml` and in the defaults of `ProcessorConfig`, which a test keeps equal; after it the measured values replace them in both places.

**Multi-rate updates (REQ-PROC-006).** The loop runs at 50 Hz; the barometer and IMU are read every cycle and the GPS fixes once per second. `process()` therefore predicts every cycle and applies each sensor only on a cycle in which its channel is NOMINAL *and* its reading is fresh (`read_ok`, Section 7). The filter cannot tell a copy from a new sample: re-applying one reading N times shrinks the covariance as if N sensors had agreed and pins the state to a value that is no longer current. With these constants, a 1 Hz fix applied 50 times would carry the information weight of a 0.7 m sensor (R/50 = 0.5 m²) in place of the 5 m sensor it is; a 500 ms barometer dropout inside the timeout window, re-applied 25 times, would leave the altitude variance at 0.061 m² where prediction alone gives 0.101 m², and during a 2 m/s climb would leave the estimate 0.25 m low with the velocity at 1.875 m/s, where prediction alone is right to the millimeter. Until 2026-10-11 the gate was on status only, and the simulator produced a fresh GPS fix on every frame, so no test could see it (FTS-VR-001 Entry 7). The filter is also constructed on the first cycle with a fresh NOMINAL barometer reading, not on the first frame: a real driver reports `read_ok` false until its first successful transaction, and a filter born from an unmeasured pressure would start 44 km up. Until then the fused fields keep the zero every source leaves in them.

**Verified behavior.** Fused altitude sigma is 0.23 m against 1.73 m raw barometric over 500 simulated frames with the 1 Hz GPS (0.24 m against 1.65 m before the simulator's GPS went to 1 Hz on 2026-10-11; the seed-42 sequence shifted when GPS noise stopped being drawn on every frame). Two runs are bit-identical. See TC-007 and FTS-VR-001 Entry 7.

## 6. Complementary Filter Design

`ComplementaryFilter` (`src/processing/complementary_filter.h`) estimates pitch and roll (REQ-PROC-002).

**Axis and sign convention.** Right-handed body frame: x forward, y right, z up. Pitch is rotation about y and integrates `gyro_y`; roll is rotation about x and integrates `gyro_x`. Accelerometer tilt uses `atan2(accel_x, sqrt(accel_y² + accel_z²))` for pitch and the y-axis equivalent for roll. **This convention is an assumption.** Whether the mounted MPU6050 agrees in sign cannot be confirmed without hardware. If it does not, the gyro and accelerometer paths fight and the filter converges to garbage; the fix is a sign flip in configuration, and the check is part of hardware week.

**Alpha as a time constant.** The gyro weight alpha (`processing.complementary_alpha`, 0.98 in the shipped file) is meaningless without the sample interval. The accelerometer correction has a time constant of about alpha × dt / (1 − alpha), which at 50 Hz is about one second. A steady gyro bias b settles to an error of alpha × b × dt / (1 − alpha) rather than growing without bound. TC-006 verifies that closed form.

**First-frame seeding.** The first update adopts the accelerometer angles directly. Starting from zero would leave the display wrong for about one time constant after boot, for no benefit.

**DEGRADED behavior and the FAULT-006 conflict.** When the IMU channel is DEGRADED the filter is not updated and the previous angles are held. FAULT-006 in FTS-FM-001 requires the opposite: attitude marked invalid, not held, so the display shows a clear failure rather than a frozen reading that looks live. The frame has no validity marker to carry that today. Hold is the interim behavior and this conflict is recorded as an open decision (Section 12). FAULT-007's accelerometer-only fallback for a stuck gyroscope is likewise not implemented.

**Stale frames (REQ-PROC-006).** A NOMINAL IMU frame whose read failed carries the previous sample. The filter is not updated on such a frame: the angles are held, and the processor remembers the time of the last sample it accepted, so the next fresh frame integrates the gyroscope over the whole gap rather than over one loop period (three stale frames at 50 Hz and a 1 deg/s rate give 0.0784°, not 0.0196°; `ComplementaryTest.GyroIntegratesOverStaleGap`). The same bookkeeping covers a DEGRADED span shorter than the timeout: the first fresh frame after recovery integrates one rate sample over the whole span, which the accelerometer term corrects within about a time constant. Integrating over one period instead would lose the rotation outright. Longer gaps are a different case, next.

**Long gaps re-seed (REQ-PROC-002).** The gyroscope integral rests on the assumption that one rate sample describes the whole interval, and past the communication timeout it does not: one sample multiplied by a ten-second outage, with an uncalibrated MPU6050 offset of several degrees per second in it, would put tens of degrees of false tilt on the display at the moment of recovery. So when the interval since the last accepted IMU sample exceeds the IMU timeout (500 ms, the same `FaultDetectorConfig::i2c_timeout_ms` the detector uses; `main` hands one config object to both, and a `static_assert` keeps the two defaults equal), the processor calls `ComplementaryFilter::reset()` before the update. The filter forgets its seed and keeps its angles, and the update adopts the accelerometer's tilt outright, exactly as the first frame after boot does; an unusable accelerometer on that frame holds the old angles until a usable one arrives. Two asymmetries follow from measuring the gap at the processor rather than the detector. The detector judges a timeout at the failing frame and the processor at the next accepted one, so a dropout the detector tolerated (failed reads from 20 ms to 500 ms) followed by a good read at 520 ms re-seeds although the channel never left NOMINAL. And the processor's gap includes DEGRADED time, so any DEGRADED span longer than the timeout re-seeds on the first NOMINAL frame after recovery whatever the fault was; the recovery frames themselves (M = 5, fresh but still DEGRADED) are not accepted and lengthen the gap. `ComplementaryTest.LongImuGapReseedsFromAccel`, `GapEqualToTimeoutStillIntegrates`, and `ReseedAdoptsTiltedAccel` (TC-006 steps 5 to 7). Decided 2026-10-11 on review of the freshness gate: FTS-VR-001 Entry 7 §7.6 had recorded the re-seed as not planned, and Entry 8 records the change of mind.

**Why not a quaternion EKF.** A full attitude estimator would handle yaw, large angles, and coupled rotations. For a board on a desk and a PFD attitude indicator, pitch and roll from a complementary filter are sufficient and every line is explainable. A production flight system would upgrade; the interface (`pitch_deg()`, `roll_deg()`) would not change.

## 7. Health Representation

Channel health is a `ChannelStatus` enum (NOMINAL, DEGRADED) per sensor inside `TelemetryFrame`. This is deliberately minimal: it is what the filters need to gate on, and nothing more. Only the fault detector writes it.

Alongside status, each channel carries a `read_ok` flag. This is not health. It says whether the driver obtained a fresh reading this cycle; `false` means the channel's fields are stale from the previous cycle. One failed I2C transaction is normal, so a source reports the fact and the detector decides when staleness has lasted long enough (the I2C timeout, 500 ms by default; longer for the 1 Hz GPS) to be a fault. Keeping the two separate is what lets the transient tolerance of REQ-FAULT-001 live in one place instead of in every driver. The processor honors the same flag: a reading is applied as a measurement only on the cycle it was obtained (REQ-PROC-006, Section 5), so health and freshness gate the filters independently. A NOMINAL channel is often stale (the GPS on 49 of 50 cycles), and a DEGRADED channel can carry fresh readings while it recovers.

Fault events (REQ-FAULT-004: timestamp, channel, type, value) are `FaultEvent` structs the detector accumulates and hands out through `take_events()`. Tests assert on the structs and `main` prints them; the binary logger will persist the same structs when it exists.

Two forthcoming needs do not fit inside the frame: the redundancy voter (Section 9) must report per-lane state, and FAULT-006 needs per-field validity. The decision between extending the frame and adding a separate `SystemHealth` sidecar struct is deferred to Sprint 2 week 1, when the voter is the first consumer. The criteria: whether the log format should carry health inline, and whether the display needs health at a different rate from telemetry.

## 8. Determinism

Same-platform replay is bit-exact. `KalmanTest.DeterministicOutput` runs the pipeline twice with the same seed and compares every fused altitude with exact equality.

Cross-platform determinism is not guaranteed and is not attempted. `std::normal_distribution` is implemented differently in libc++ (macOS) and libstdc++ (Linux, Raspberry Pi), and `std::pow` and `std::atan2` may differ in the last bit between math libraries. A log recorded on the Pi and replayed on the Mac may therefore differ at the least significant digits. This is documented here and in the simulator source, and TC-004 is scoped to same-platform replay. Replacing the standard distribution with a hand-written generator was considered and rejected: the property that matters, live-to-replay equality on the Pi, does not need it.

## 9. Log Format and Replay

The binary log (REQ-LOG-001) is a header followed by tagged records:

```
LogFileHeader (16 bytes): magic "FTLG", format version, sizeof(TelemetryFrame),
                          sizeof(FaultEvent), reserved, endianness marker
{ tag (1 byte), record }   tag 1 = TelemetryFrame (104 bytes), tag 2 = FaultEvent (16 bytes)
```

**Raw struct records.** Both record types are written as their in-memory bytes. That is licensed by `static_assert(std::is_trivially_copyable)` on each: the bytes are the value. It is the simplest correct format for the scope this project claims (Section 8: same platform, same build), and it costs nothing per frame. Field-by-field serialization with fixed widths would be portable across compilers and byte orders and is the right answer for a shipped product; it was considered and deferred as roughly three times the code for a property the project does not claim.

**Padding bytes.** Both on-disk structs contain padding the compiler inserts for alignment: `TelemetryFrame` (104 bytes) has four bytes before `latitude` and six after `gps_read_ok`; `FaultEvent` (16 bytes) has two between `type` and `value`. Nothing assigns those bytes. An object declared without an initializer carries stack garbage in them, and so does a braced temporary on GCC, and the logger writes them verbatim. Rule: **every struct that reaches the logger is value-initialized (`T x{};`) and then assigned, never brace-built or left default-initialized**, so padding is zero and the bytes are a function of the fields alone. Two guards: `SimulatedDataTest.SameSeedSameSequence` (frames, `memcmp` of two same-seed frames) and `FaultDetectionTest.EventPaddingBytesAreZero` (events, checks the padding bytes directly). Each found a real instance on 9/9: the simulator's uninitialized frame on the Mac, and the detector's brace-built events on Linux in CI. A future format version should replace implicit padding with explicit reserved fields so the layout has no unspecified bytes at all (Section 12).

**Header guards.** The header carries everything a reader needs to refuse a file rather than misread it: magic so a wrong file fails instantly, a version so the format can evolve, both record sizes so a frame-layout change is caught at open time, and an endianness marker for honesty about the platform limit. **Rule: any change to `TelemetryFrame` or `FaultEvent` bumps `kLogFormatVersion` in the same commit.** The `read_ok` flags added on 9/9 were the last free frame change.

**Rotation (REQ-LOG-002)** happens before a record that would push the file past the configured limit, never in the middle of one. A torn record makes the tail of a file unreadable and a replay would silently lose a frame. Every file, rotated ones included, starts with its own header, so each is readable alone and `list_log_files` returns them in name order (`prefix_000.bin`, `_001`, ...).

**Fault events** (REQ-FAULT-004) are tag-2 records in the same stream, so an event sits between the frames it occurred at. Replay skips them and reproduces them by re-running the detector; the identity test compares the reproduced events to the logged ones.

**On the wire (REQ-TRANS-001).** The ZeroMQ publisher (`src/transport/zmq_publisher.h`) sends each processed frame as one message laid out as a complete one-record log file: the 16-byte header, the FRAME tag, the 104 frame bytes, 121 bytes in all. Pub/sub has no handshake, so a subscriber that joins late gets no once-per-connection header; carrying the header on every message lets any subscriber validate version, record sizes, and byte order from the first message it sees, with the same parser it uses for a log on disk. One layout, one Python module, one constant to bump. The cost is 17 bytes per message, 850 bytes per second at 50 Hz. Fault events are not published: no requirement asks for them on the wire, the frame's status fields already carry channel health, and the tag byte means adding them later is one more message type, not a format change. ZeroMQ calls a message part a "frame"; in this project "frame" is always `TelemetryFrame` and ZeroMQ's unit is a message. The message is assembled by one function, `frame_message` in `log_format`, so the two transports cannot disagree by a byte.

**The second transport (REQ-TRANS-002).** The UDP publisher (`src/transport/udp_publisher.h`) sends the same 121-byte message as one datagram per frame, which is under every MTU (IPv4 guarantees 576 bytes, Ethernet carries 1500), so a frame is never fragmented and arrives whole or not at all. The socket is *connected* at startup: `connect` on a datagram socket sends nothing, it records the destination and the route so that each `send` needs no address, and it is what makes the kernel deliver this destination's ICMP errors to this socket. It also fixes the source address at startup, so a board that re-addresses its Wi-Fi mid-run fails every send until restart, counted. The destination is one unicast IPv4 address and port (`--udp <ipv4>:<port>` until REQ-CFG-001): `0.0.0.0` and `255.255.255.255` are refused by name; `SO_BROADCAST` is not set, so a kernel that recognizes a directed broadcast refuses it (Linux, at connect) while one that routes it like unicast delivers it (macOS does for the loopback's 127.255.255.255); multicast is not configured. Telemetry downlinks use datagrams for the property a stream cannot give: a frame that could only be delivered after the next one is due is stale, and TCP would hold fresh frames behind a lost old one. Loss and reordering are the receiver's to measure, from the timestamps; the receiver counts a backwards step as out of order. No sequence number travels on the wire (Section 12).

**The transport seam.** `Publisher` (`src/transport/publisher.h`) is the output-side twin of `DataSource`: one virtual `publish`, one `stats`, a virtual destructor. The loop holds a vector of `Publisher*` and never learns which transports it has; `main` owns the concrete objects, checks each one's `ok()` at startup, and prints each one's summary at exit. `--zmq` and `--udp` may be given together. A third transport is a class and a flag, not a loop change.

**Publishing never blocks the loop (REQ-TRANS-003).** The publisher is a PUB socket, whose send never waits (zmq_socket(3)): when one subscriber's queue reaches the send high-water mark, messages to that subscriber are dropped until it catches up, other subscribers are unaffected, and with no subscriber at all every message is dropped on the spot. The mark is 100 messages, two seconds of frames, so a subscriber that stalls briefly loses nothing and one that falls further behind loses frames rather than slowing the loop; the library's default of 1000 would hold 20 s of stale frames, and a conflating socket (newest message only) would break TC-005's every-frame check. Those drops are silent at the sender, so the publisher counts only what it can see, messages accepted and sends refused, and loss is measured at the receiver from gaps in frame timestamps. A failed bind at startup is reported and `main` exits; a failed send inside the loop is counted and the cycle continues. The socket's linger is 500 ms: context termination at exit waits at most that long for messages the I/O thread has not yet written, instead of the library's default of forever (a stuck subscriber would hang exit) or zero (the last frames of a healthy run could be discarded). cppzmq reports errors by throwing; the publisher translates both failure paths into status and counters at its boundary, and both are reachable from unit tests (an endpoint already bound, a context shut down), so no coverage exclusion hides them. The UDP publisher sends with `MSG_DONTWAIT`, the kernel's form of the same flag: a datagram is queued whole or refused with an error code, never waited on. What the kernel can refuse, and when, differs from ZeroMQ: a full send buffer (EAGAIN; never on loopback, where delivery is synchronous); a port nobody listens on, which the kernel learns from an ICMP unreachable after the fact and reports on a *later* `send` as ECONNREFUSED, one report per ICMP, that datagram not sent; a non-unicast destination (EACCES, at connect on Linux and at the first send on macOS). A receiver whose kernel buffer is full drops on its own side and the sender sees nothing, exactly as a PUB socket at its mark. Every refusal is counted with its errno, never retried, and the cycle continues; the one branch no configuration can reach, `socket()` failing, is reached in a unit test by lowering the process's descriptor limit. One correction to the ZeroMQ figure above for `tcp://`: the kernel's TCP buffers on both ends sit between the two high-water marks and hold minutes of 121-byte frames, so at process level a subscriber that stalls for seconds loses nothing, and the 100-message mark is reached only by a burst (FTS-VR-001 Entry 6 run d) or over `inproc://`, where there are no kernel buffers (TC-010 step 4).

**Replay strips to raw.** `LogReplaySource` zeroes every computed field and resets every `ChannelStatus` to NOMINAL before a frame leaves it, keeping the timestamp, sensor fields, and `read_ok` flags. This is the raw-only contract of Section 3 applied to replay: the detector recomputes status from `read_ok` (observation, kept) and the processor recomputes the rest. A replay that passed the logged results through would let the pipeline be skipped entirely and still "match."

**Verified behavior.** `ReplayTest.ReplayReproducesLiveSession` logs 500 simulated frames with an injected barometer dropout and a stuck IMU across rotated files, replays them through a fresh detector and processor, and finds every processed frame and every fault event bit-identical. At file level, `telemetry` followed by `telemetry --replay logs/telemetry_000.bin` produces `logs/replay_000.bin` byte-identical to the original. A replay run logs under a different prefix so that session A and session B sit side by side; the replay source opens its input lazily, on the first read, after the logger has opened its output, so the prefixes are what keep the two apart, and `main` refuses to replay a `replay_NNN.bin` from the output directory rather than destroy it.

**The recorded configuration (REQ-CFG-003).** The computed fields are a function of the raw frames, the code, and the configuration. The header pins the code's layout and the frames are the data; the configuration is pinned by a copy of the file's text, verbatim, written beside the log as `<prefix>_config.yaml` once the logger has opened (`logs/telemetry_config.yaml` for a session, `logs/replay_config.yaml` for a replay; one record per directory and prefix, which the Python reader's name rule ignores). `--replay` reads that record by default and the `Configuration:` line says so; `--config` with `--replay` reads the named file instead, and the line says whether its text equals the record (the same configuration under another name), differs (a legitimate run, which is how FTS-NP-001 chooses the initial velocity variance, but not an identity claim), or has no record to compare with. A log with no record and no `--config` is refused naming the expected path. Identity (REQ-LOG-003) is a property of the configuration's text, not of its path.

**End of stream.** `DataSource` has no way to say "no more frames." After the last frame, `read_frame()` returns that frame again and `exhausted()` reports true. Adding an end-of-stream signal changes the interface every source implements and is an open decision (Section 12).

## 10. Fixed-Rate Timing

The processing loop runs on a fixed period (REQ-TIME-001; `timing.period_ms`, 20 ms in the shipped file) with per-cycle jitter measured and logged (REQ-TIME-002). Three components: a `Clock` interface at the OS boundary, a `FixedRateScheduler` that owns the deadline arithmetic, and a `JitterLog` that records what each cycle measured.

**Absolute deadlines, not relative sleeps.** Every deadline is `start + n × period`, produced by adding the period to the previous deadline. A loop that slept "period" after its work would run at `period + work + wake latency` per cycle, and that error would add up: 5 ms of work and 0.3 ms of latency drift 5.3 seconds over 1000 cycles. With a fixed grid each cycle's lateness is independent and never accumulates. `TimingTest.DeadlinesAdvanceByExactPeriod` states this in numbers.

**The `Clock` seam.** The scheduler never calls the OS. It calls `Clock::now_ns()` and `Clock::sleep_until_ns()`, the same way the pipeline calls `DataSource::read_frame()` and never a sensor. Tests substitute a fake whose time moves only when the test says so, so a thousand scheduled cycles run in microseconds. This is the injectable clock FTS-TP-001 §2.1 asks for, applied to the one component that needs it; the fault detector reads time from frame timestamps instead (Section 4).

**Linux and macOS sleep primitives.** On Linux, `MonotonicClock::sleep_until_ns` is `clock_nanosleep(CLOCK_MONOTONIC, TIMER_ABSTIME, ...)`, re-issued on `EINTR`. The kernel is given the absolute target, so nothing between reading the clock and sleeping can lengthen the wait. That is the call REQ-TIME-001 names, and it runs on the Raspberry Pi and in CI. macOS has no `clock_nanosleep`; the fallback re-reads the clock and calls `nanosleep` for the remainder until the target is reached. The scheduling logic is identical; only the sleep primitive is weaker, because a preemption between the read and the sleep lengthens that one wait. The `#if defined(__linux__)` inside that function is one of two platform splits in the codebase; the other is the I2C device file in `src/drivers/i2c_bus.cpp` (Section 3). Both sit on an operating-system boundary, and nothing above either differs between platforms. The 1 ms bound of REQ-TIME-003 is claimed only for the Linux path.

**Overrun policy.** If the loop comes back a whole period or more after its deadline, the scheduler skips the deadlines that already passed, reports how many (`missed_cycles`), and keeps the grid. It never fires back-to-back cycles to catch up. A control loop that fell behind and then burst would be worse than one that missed cycles and said so; a telemetry logger gains nothing from the burst either.

**Jitter in a CSV, not the binary log.** Jitter measures this machine on this run. The binary log is the record of the flight and must replay byte-identically (Section 9). Putting non-deterministic timing records into it would make two identical flights produce different logs. So each live run writes `telemetry_jitter.csv` beside the log in `logging.directory`, one line per cycle, and prints a min/mean/max/missed summary at exit. The CSV loads straight into numpy for the characterization run on the Pi.

**Replay is unpaced.** Logged frames carry their own timestamps; every time-dependent computation reads those, so pacing a replay would add nothing to the identity check. `run()` takes the scheduler and jitter log as nullable pointers; replay passes null. A replay that also publishes (`--replay` with `--zmq` or `--udp`) therefore sends its frames as a burst, as fast as the log reads, and the receiver's gap count shows what a slow subscriber lost. Pacing a replay is a display feature (Section 12).

**Frame timestamps stay with the source.** The simulator stamps 0, 20, 40 ms as before; pacing makes wall time agree with it. The live source stamps the actual read time: `Clock::now_ns()` at the top of `read_frame()`, from the same `MonotonicClock` the scheduler paces on, as milliseconds since the source's first frame (frame 0 is 0, like the simulator), rounded to the nearest millisecond in integer arithmetic. Decided with the live source (Section 12) over the scheduler's deadline grid for three reasons: the source cannot see the deadline, since `read_frame()` takes no arguments and a setter would leak scheduling into every `DataSource`; the frame should say when the data was taken, so an overrun shows as a 40 ms step that the Kalman prediction and the gyroscope integral then account for, and the detector's timeouts are judged on real elapsed time; and the receiver's gap count uses floor division, so jitter under a period never counts and a missed cycle counts as exactly one. The cost is a `dt` of 20 ms plus or minus the jitter instead of exactly 20, which both filters already take from the timestamps. The jitter CSV remains the timing evidence (REQ-TIME-002); the frame carries when the data was taken.

## 12. Open Design Decisions

- **Health sidecar vs frame fields.** Decide in Sprint 2 week 1 (Section 7). Blocks FAULT-006 compliance and voter reporting. Any frame change now also bumps the log format version (Section 9).
- **Live source timestamps: scheduled vs actual.** Decided with the live source (2026-10-12): the actual read time from the monotonic clock, as milliseconds since the source's first frame (Section 10). The grid would hide overruns and needs a setter on every `DataSource`; the read time is truthful and self-contained, and the receiver's gap counter tolerates the jitter.
- **Real-time replay.** Decided with the transport work (2026-10-11): replay stays unpaced, and a replay that publishes does so as a burst (Section 10). Driving a display from a replayed log needs pacing at the original rate, which is the scheduler with the log's own timestamps as deadlines; that arrives as a `--pace` flag with the Primary Flight Display, not before.
- **Transport tuning in configuration.** Decided on the configuration day (2026-10-13): the ZeroMQ high-water mark (100 messages) and linger (500 ms) stay named constants. REQ-CFG-001 lists transport addresses and ports, and those are keys (`transport.zmq.endpoint`, `transport.udp.host` and `.port`, each with an `enabled` switch), which `--zmq` and `--udp` enable and override for one run. A key without a requirement is scope; the tuning joins the file when a requirement asks for it. The UDP host stays an IPv4 dotted quad (no name resolution).
- **Explicit reserved fields in on-disk structs.** `TelemetryFrame` and `FaultEvent` rely on the value-initialization rule to keep implicit padding zero. The next format version should add explicit `reserved` bytes so the structs have no padding at all and the rule becomes unnecessary. Frame change, so it waits for the sidecar decision and a version bump. The header's own `reserved` field stays zero; using it as a wire-only sequence carrier was considered with the UDP transport and rejected (next bullet).
- **Per-message sequence number.** Deferred. Loss is measured at the receiver from timestamp gaps, which cannot tell a dropped frame from a scheduler overrun (the sender's jitter CSV can), and a backwards step is counted as out of order. A sequence number could live in the frame (a format version bump, so it waits for the sidecar decision), in the header's 16-bit `reserved` field (rejected: the message would no longer be a byte-exact one-record log file, and the field's job is to be zero), or in a wire-only envelope ahead of the message (rejected: two layouts, two parsers). It is added when a consumer must tell loss from overrun without the sender's CSV, which is the display or the voter, and then in the frame.
- **End-of-stream signal on `DataSource`.** Replay repeats its last frame after the log ends. A `bool has_next()` or an `std::optional<TelemetryFrame>` return would be cleaner and touches every source. Deferred when the live source landed (2026-10-12): an endless source has no end of stream, so the live source neither needs nor informs the decision; it belongs with the pacing and display work that gives replay a consumer.
- **Gyroscope saturation fault.** No FAULT entry exists for the gyro's full-scale limit (FTS-FM-001 TODO). Still open after the detector landed; FAULT-010 covers the accelerometer only.
- **GPS stuck detection.** REQ-FAULT-002 says "any channel", but no FAULT entry covers a stuck GPS and a stationary receiver, or a sample-and-hold ADS-B source, legitimately repeats. Either add a FAULT entry with a rule that tolerates legitimate repeats or narrow the requirement.
- **Bus-level fault event (FAULT-004).** Two simultaneous I2C timeouts log two events today. Collapsing them into one needs driver error codes that distinguish a bus fault from two device faults.
- **`TelemetryProcessor` configuration.** Decided on the configuration day (2026-10-13): one `ProcessorConfig` in `processor.h`, the processor being the one consumer of the Kalman variances, alpha and the sea-level reference; the file groups the six keys under `processing`, and the defaults stay for bare construction in tests (Section 3).
- **Where alpha lives.** Decided by the SRD's own words: REQ-CFG-001 names the complementary filter gain, so alpha is `processing.complementary_alpha`, handed to the filter by the processor; the filter keeps its default for bare construction in tests.
- **Accelerometer-only fallback (FAULT-007).** Requires the detector to distinguish a stuck gyroscope from a stuck accelerometer, which the single DEGRADED state cannot express. Tied to the sidecar decision.
- **Barometer chip identity: BMP280 in the documents, a BME280 board on the bench.** FTS-SRD-001 (the channel definition, REQ-SENS-001, REQ-SENS-002 and its rationale), FTS-FM-001 (FAULT-001, FAULT-004, FAULT-005, FAULT-008, FAULT-009, the degradation matrix), FTS-TP-001 (scope note, TC-001 objective), FTS-TM-001 (SENS-001 and SENS-002 rows), the Section 3 table above, and comments in five source files and two test files all name the BMP280. The board on hand is a HiLetgo GY-BME280. Bosch's BME280 datasheet (BST-BME280-DS001-24 §5.2, Table 17) states the BME280 is downward register compatible with the BMP280, with pressure and temperature control and readout identical, and lists the exceptions: chip ID 0x60 instead of 0x58 (BMP280 datasheet BST-BMP280-DS001-26 §4.3.1), standby codes `110`/`111` meaning 10 ms/20 ms instead of 2 s/4 s, and 20-bit output whenever the IIR filter is on. I2C addressing (0x76/0x77 by SDO) and the temperature and pressure calibration layout at 0x88 are the same; the temperature and pressure compensation code is identical in the two datasheets (BME280 §4.2.3 and BMP280 §3.11.3, compared line by line), so the barometer compensation card's primary oracle, the worked example on page 23 of BMP280 datasheet revision 1.14 (document BST-BMP280-DS001-11, May 2015), serves either chip. That example's measurement table swaps the UT and UP register addresses, a typo a Bosch Sensortec community moderator confirmed on 2022-01-03 and said will not be corrected because the BMP280 is discontinued; the Week 2 map carries the corrected addresses. The BME280's humidity has no requirement and is not read. Cheap boards are sometimes mislabeled, so the chip ID read on the first hardware day decides. If it reads 0x60: name the driver and the compensation card after the BME280, re-check the FAULT-008 and FAULT-009 limits against the BME280 datasheet, reword every BMP280 mention listed above, and bump the SRD version as a wording revision. If it reads 0x58: close this decision and change nothing. Until then the documents keep saying BMP280. **Provisional values (2026-10-12), built before the first hardware day:** the driver is `Bmp280` and accepts both identities, 0x58 and 0x60, reporting which answered through `chip_id()`; `config/telemetry_config.yaml` addresses the barometer at 0x76 and the MPU6050 at 0x68 (`sensors.*.address`, the `SensorConfig` defaults following them by test), and the driver expects WHO_AM_I 0x68 (the board is marked HW-611, usually a BMP280, and the GY-521's AD0 is low). The Pi's `i2cdetect` and `i2cget` readings (TC-014 step 11) either confirm these or land the BME280 rename and any address change (the file and the defaults together) as a small follow-up commit; this bullet stays open until they do.
- **Gyroscope bias handling.** The stationary capture measures the gyro's bias per axis; the complementary filter turns a bias b into a steady tilt of 0.98 × b degrees (Section 6), and the MPU-6050's datasheet allows ±20 deg/s part to part with ±20 deg/s of variation over temperature. Nothing is subtracted yet. Rule (FTS-NP-001 Section 3): if 0.98 × |b| exceeds 1° on either axis, a requirement for subtracting a configured per-axis bias is proposed, conditional on a second capture on another day agreeing within 0.2 deg/s; below 1° the accelerometer term already holds the error. Estimating the bias at startup is not planned (it assumes a still vehicle at boot and needs its own fault mode); the lasting fix is a bias state in the filter.
- **Replay of a rotated session from the CLI.** `--replay` takes one file: `LogReplaySource` can span rotated files, but `main` hands it a single path, and a `--cycles` count beyond the file's frames repeats the last frame with the same timestamp. A rotated capture is therefore analyzed as one run in Python but replayed one file at a time (the noise capture's file 000, 9,986 frames). A directory or prefix argument to `--replay` is a `main.cpp` change that belongs with the pacing and display work. A session's configuration record is one file per directory and prefix (Section 9), so a rotated session shares one record.
