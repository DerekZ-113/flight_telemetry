# CLAUDE.md — Flight Telemetry System

## What This Project Is

Embedded flight telemetry for a Raspberry Pi in C++17, built with DO-178C-aligned practices: every line of code traces to a written requirement and to a test, and structural coverage, static analysis, and a formal fault model are part of every build.

**Built:** the 120-byte `TelemetryFrame` record (format version 3: the version-2 bytes as its prefix, the source's sequence number, a flags byte, the ADS-B vertical rate and pressure altitude, the GPS fix quality and satellites, the voter's status, one reserved field); the `DataSource` abstraction with a simulated source, a fault-injecting decorator, and a log-replay source; the processing pipeline (ISA pressure-to-altitude, 2-state Kalman altitude/velocity fusion, complementary-filter pitch and roll); the fault detector (communication timeout, stuck value, range, recovery; since 2026-10-19 a reading that is not a finite number is OUT_OF_RANGE before any other test) with per-channel DEGRADED state; three identical processing lanes behind the one detector and a majority voter (REQ-RED-001 to REQ-RED-006): every frame processed by all three in the loop's thread, compared bit for bit in the thirteen fields a lane writes or carries, the checked frame emitted with the majority's computed fields, a lane outside the majority on three consecutive majority cycles excluded until restart, no majority held under FAILURE_WARNING and flagged, an overrun told by the frame's identity, the decisions in the frame's `voter_status` (recomputed on replay) and the voter's events on new values of the fault event's bytes, a lane-fault interface the binary uses only under `--lane-fault <lane>@<seconds>`, which records the injection in the log and whose replay re-applies it (REQ-RED-007), the voter panel on the PFD; a seeded Monte Carlo fault-injection campaign (`tests/fault_injection/`, `fault_campaign`; REQ-TEST-005, REQ-TEST-006) that runs the real simulator, detector, lanes and voter in one process over 93 cells (the detector's faults, faults below each threshold, faults no check covers, clean runs, lane faults at persistence 1 to 8), one seed per run that alone rebuilds it, predictions committed before the code, a fixed subset of 450 runs gating every build, and a report (`docs/fault_injection_report.md`, FTS-FI-001) whose tables and figures `analysis/fault_campaign.py` regenerates from a campaign's record, its preview of 2026-10-19 recorded; a binary logger with rotation, a reader, and bit-identical deterministic replay; a fixed-rate scheduler on absolute deadlines with per-cycle jitter logging; two transports behind one `Publisher` seam: a ZeroMQ publisher that sends every processed frame as a one-record log message on a PUB socket, and a UDP publisher that sends the same message as one datagram to a unicast destination over a connected non-blocking socket, neither ever blocking the loop, with a Python receiver that reads either transport through the log's byte layout; an `I2cBus` seam with a Linux device-file implementation and a test fake, the BMP280 (BME280-compatible) and MPU6050 drivers verified against the manufacturers' arithmetic, and a live sensor source selected by `--live`; an ADS-B source selected by `--adsb` that presents one real aircraft from the OpenSky Network's REST API as the GPS channel through the same seam (an `HttpClient` seam with a libcurl implementation and a test fake, a JSON parser that never throws, an OAuth2 token client whose secret lives in a file outside the repository and travels only in the token request, selection with hysteresis among the descending aircraft in a configured box, sample-and-hold under the freshness rule on the project's one thread with a mutex-guarded handoff, every switch recorded beside the log, announced in the session status and flagged on the new aircraft's first frame so every filter is reborn on it, the broadcast's vertical rate and pressure altitude recorded as raw fields, the barometer and IMU reported NOT_AVAILABLE; verified on a local stand-in and on a live run, CI never calling the service); a `SerialPort` seam (POSIX termios in raw mode, non-blocking, no platform split, unit-tested on a pseudo-terminal), the NMEA 0183 parser verified against the u-blox manual's printed examples, and the `NmeaGps` driver that frames sentences out of the byte stream, pairs the GGA and RMC of one epoch and hands the live source one fresh reading per valid fix at the receiver's own 1 Hz, the receiver named by three `sensors.gps` keys and off in the shipped file; a Python log reader that is the C++ reader's twin, the replay-identity pytest, the noise analysis (per-channel sigma, Allan deviation, gyro bias, the derived Kalman constants) verified against simulated logs, and the transport pytest over both transports; one YAML configuration file (`config/telemetry_config.yaml`, 48 keys, ten of them in an optional `adsb` block) loaded and validated at startup, handed to every module by constructor, and recorded beside each session's log so a replay runs with the configuration its log was recorded with; a validity byte per computed field in the frame, written by the processor in order of precedence (NO_COMPUTED_DATA, FAILURE_WARNING, NORMAL) so a display can tell a value from its absence, NO_DATA on a channel before its first reading, NOT_AVAILABLE on a channel the source does not provide (no fault event, a no-source flag on the display), and log format version 3, whose header records the run mode and the mode the frames were produced in, while readers still replay version-1 and version-2 logs as a prefix; a replay that ends at its log (`DataSource::has_next()`, a one-frame look-ahead in the replay source, `--cycles` as a cap) and, with `--pace`, is released on the log's own timestamps through the `Clock` seam by a `TimestampPacer`, the paced log byte-identical to the unpaced one and its lateness in `logs/replay_jitter.csv`; a nineteen-byte session status on both transports (version 3: the run mode LIVE, SIMULATED, REPLAY or ADSB, the source mode a replay carries forward from its log's header and, in ADS-B mode, the selected aircraft's identity, before the first frame, once a second and at once when the aircraft changes, ENDED three times after the last; never a log record), which the receiver reads and ends on; a WebSocket bridge (`pipeline/bridge.py`, Python `websockets`, loopback by default, latitude and longitude never forwarded) and a React page (`dashboard/`, Vite and TypeScript, Vitest) showing frames arriving: the mode label (with the aircraft's identity in ADS-B mode, `ID UNAVAILABLE` in a replay of an ADS-B recording), the feed's state (stale from the page's own arrival clock, ended from the status), the rate, the last frame, each computed field with its validity by name, each channel's status; the Primary Flight Display's instruments (`dashboard/src/pfd/`: an attitude indicator, an altitude tape (labelled `ft HAE` whenever the frames came from the ADS-B source, live or replayed), a vertical speed indicator, a ground speed readout, a track indicator and a ground track plot relative to the first fix, each showing a value only while its validity or channel status allows it and a flag naming the instrument otherwise, specified in `docs/display_spec.md`), the lag check beside the stale one, and the simulator's scripted flight (`--motion demo`, the pipeline's own models inverted, the stationary default byte-identical) for the replay demo; Google Test unit tests, a pytest suite and the page's Vitest tests, all run in CI on every push; CI with a branch-coverage gate and cppcheck; nine controlled documents under `docs/`.

**Planned:** the fault-injection campaign of record, rerun after the stationary capture's constants land (TC-036); the three lanes' cost on the Pi (TC-009 step 8); the GPS receiver's first fixes on the Pi (USB or the header UART) and the board's capture as a test fixture; the stationary capture that feeds the measured constants into the configuration file; the v0.2.0 demo video from the replay demo; a Chrome background tab's lag, a hand measurement (TC-025 step 8); ADS-B Phase B, the vertical rate the frame records since format version 3 as the filter's third measurement, the pressure altitude and the selection's altitude term (design §12). ## The One Rule That Matters

**Never write code without a requirement.** Every feature starts with a requirement ID in `docs/requirements.md`, then code, then test, then traceability update. If a feature isn't in requirements.md, it either needs a requirement added first or it doesn't belong. This is the DO-178C discipline and it's non-negotiable for this project.

## DO-178C Workflow — The Loop

Every feature follows this exact sequence:

1. Add requirement to `docs/requirements.md` (REQ-XXXX-NNN format)
2. Add row to `docs/traceability_matrix.md` (empty implementation/test columns)
3. Write the code
4. Update traceability with implementation file/function
5. Write the test (Google Test for C++, pytest for integration)
6. Update traceability with test file/function
7. Run coverage (gcov/lcov), run static analysis (cppcheck)
8. Commit everything together, naming the requirement IDs in the message

## Coding Conventions

- C++17, `-Wall -Wextra -Wpedantic`; CI adds `-Werror` (`WARNINGS_AS_ERRORS=ON`)
- `const&` for passing structs/objects to functions (no unnecessary copies)
- RAII for resource management (I2C bus handles, file handles)
- Header (.h) and implementation (.cpp) split for all classes; every class gets its own pair
- snake_case for files and variables, PascalCase for classes and structs
- Comments explain WHY, not WHAT — the code should be readable on its own
- **Value-initialize every struct that reaches the logger, then assign its fields:** `TelemetryFrame frame{};`, `FaultEvent event{};`. Records are written as raw bytes; since format version 2 neither struct has padding (every former padding byte is a named `reserved` or validity field, and a `static_assert` that the members sum to the size proves it), so the rule now keeps the reserved fields zero rather than invisible bytes. Found twice in Week 1 (`docs/verification_results.md` Entries 4 and 5); guarded by `SimulatedDataTest.SameSeedSameSequence`, `FaultDetectionTest.EventReservedIsZero` and `FrameLayoutTest.EveryByteIsANamedField`. A reserved field means zero until a format version assigns it; any change to either struct bumps `kLogFormatVersion` in the same commit. A new enumerator in an existing byte is not a change to the struct: `ChannelStatus::NOT_AVAILABLE` (2026-10-15) and the voter's event values (`Channel::VOTER` and four `FaultType`s, 2026-10-18) moved no byte and bumped no version, and a reader older than the value prints its number; a new record tag would be a format change, since both readers refuse an unknown one.
- **Mark GCC exception edges on conditional lines.** A line that combines a conditional with a `std::string` temporary, a standard-library call, or an iterator range shows untaken exception-unwind branches on GCC that `lcov --filter branch` cannot remove. Put `// LCOV_EXCL_EXCEPTION_BR_LINE` on that line with a one-line reason and list it in `docs/verification_results.md`. Never add `--rc no_exception_branch=1` to the workflow: on the runner's lcov 2.0 it discards all branch data (Entry 5 §5.5 and §5.6).
- Python code follows standard PEP 8. Every module under `pipeline/` and `analysis/` has a row in the matrix's Python reverse-trace table, and a pytest file is named in the Test column of the requirement it verifies, exactly as the C++ files are.

## Key Architecture Decisions

- **Data source abstraction:** abstract base class so the processing engine doesn't know if it's reading live sensors or replaying from a binary log. Sources fill raw fields, `read_ok`, the sequence number and the flags byte only, leaving status NOMINAL (unjudged), every validity NOT_JUDGED, the voter's status and the reserved field zero; computed fields, health and validity belong to the pipeline. This is what lets replay use the same code path as live mode (REQ-LOG-004).
- **Drivers behind the I2C seam:** `I2cBus` is addressed per transaction (one descriptor serves the bus); drivers return `std::optional` readings and never throw, and a failed read becomes `read_ok` false with the fields held; the live source stamps frames with the actual read time from the monotonic clock; the Linux implementation sits behind the second `#if` and compiles to a stub elsewhere; the barometer and IMU addresses in `config/telemetry_config.yaml` (0x76, 0x68) and the driver's name (`Bmp280`) are provisional until the chip IDs are read on the Pi (design §12). The GPS receiver sits behind a `SerialPort` seam (`PosixSerialPort`: termios raw mode, `O_NONBLOCK`, a flush at open; POSIX, so no `#if`, and unit-tested on a pseudo-terminal); `NmeaGps` frames sentences, checks checksums, pairs the GGA and RMC of one UTC time into a fix, and the live source sets `gps_read_ok` only on the cycle a valid fix completed, holding it between; a no-fix epoch is not a reading, so the channel times out like a silent one and the `GPS:` exit line's counters tell the two apart; the receiver is `sensors.gps.enabled`, `.device` and `.baud_rate`, off in the shipped file. The first second after start is the device's backlog (a USB receiver hands over what it buffered while the port was closed, after the flush), discarded and counted; a hung-up device is read errors, which `poll(2)` tells from silence.
- **Three lanes and a voter (REQ-RED-001 to REQ-RED-006, design §13):** `RedundantProcessor` runs three `TelemetryProcessor` lanes, built element by element from the configuration (a default-built array would run the test baseline), on their own copies of the detector's frame, all three every cycle, and `Voter` chooses: `lanes_agree` compares the thirteen fields bit for bit (floats as their bits through `memcpy`, a NaN agreeing with nothing), the first agreeing pair in the order (1,2), (1,3), (2,3) names the representative, and the output is the checked frame with its ten computed fields, so the voter never writes a status and a healthy run's log differs from the single lane's in `voter_status` alone. A lane outside the majority on 3 consecutive majority cycles (`Voter::kLanePersistence`, a named constant REQ-RED-003 states, the constructor's default for the harness to sweep) is excluded until restart; no count moves without a majority, so at least two lanes always remain; with no majority the frame holds the last vote under `min(held, FAILURE_WARNING)` and NO_MAJORITY; a lane whose output carries another timestamp or sequence has overrun; a NEW_VEHICLE frame clears the held vote, not the exclusions. The voter's events are `Channel::VOTER` with four new `FaultType`s, logged after the detector's; `LaneFaultHook` (REQ-RED-005) alters a lane's input or output, for the tests and the campaign, and in the binary only under `--lane-fault` (REQ-RED-007). Three lanes on one CPU prove the mechanism and catch nondeterminism; they do not survive the Pi failing and cannot see a sensor fault.
- **The fault-injection campaign (REQ-TEST-005, REQ-TEST-006, REQ-RED-007; design §14, FTS-FI-001):** an in-process C++ engine in `tests/fault_injection/` (verification tooling: outside the coverage gate and cppcheck's `src` scan, so its evidence is its own known-answer tests) runs `SimulatedSource` behind `FaultInjectingSource`, the detector and `RedundantProcessor(tuning, imu_timeout, P, &LaneFaultInjector)` unpaced, about 1.5 µs a frame. A run's id is `cell × 100,000 + replicate` and alone rebuilds it; the schedule and the simulator's seed come from the kind and the replicate, so the six persistence counts of a lane kind share their faults and noise (common random numbers); the draws are the engine's own arithmetic over `std::mt19937` and `std::seed_seq`, which the standard fixes, so a schedule is the same on libc++ and libstdc++, while the noise (`std::normal_distribution`) is the platform's. Every prediction is a formula of the configuration, written into FTS-FI-001 Section 5 and committed before the engine existed, and never edited: a departure is a finding (Section 7). The CI subset (ten seeds per cell, the lane cells at P = 1 and 3) asserts each run's prediction; since 2026-10-18 its oracle for V09 and V12 replays the vote frame by frame, a NaN agreeing with nothing, after the subset found an identical bit flip that is NaN below 2 m, and `as_written` keeps Section 5's closed forms for the report. Every declaration falls in one bucket (detection inside the window, repeat, false alarm, wrong channel); false alarms count against exposure once per kind and replicate; rates carry Wilson intervals and zero counts the rule of three; latencies are nearest-rank, so every value reported was observed. `fault_campaign --out` writes `runs.csv`, `manifest.json` and the configuration's copy; `analysis/fault_campaign.py` rewrites only the report's `<!-- generated:NAME -->` blocks and its figures; `scripts/fault_campaign.sh` refuses a dirty tree, and `--preview` records the tree's hash instead of a commit. The demo's `--lane-fault <lane>@<seconds>` flips bit 22 of that lane's fused altitude every cycle from the first frame at or after the time, logs one LANE_FAULT_INJECTED event (FaultType 8, channel VOTER, value the lane; a new value of an existing byte), and a replay reads its input's events first (`recorded_lane_faults`) and re-applies the fault, so the replay's records equal the recording's.
- **Detector before processor:** the fault detector runs first and owns `ChannelStatus` (NO_DATA until a channel's first reading, then NOMINAL or DEGRADED; NOT_AVAILABLE is the one status a source asserts, for a channel it has no sensor for, and the detector leaves it alone with no timeout and no event, REQ-FAULT-007); the filters consume a reading only when its channel is NOMINAL and the reading is fresh (`read_ok`): predict every cycle, update at each sensor's own rate (REQ-PROC-006). The detector judges timeouts on the frame's own timestamp, never a wall clock, so replay reproduces the same faults at the same frames. Its first test on every fresh reading is finiteness (REQ-FAULT-003's clause since SRD 0.16.0, FAULT-024): a NaN or an infinity in the barometer, the IMU or a GPS fix's five fields is OUT_OF_RANGE on that frame, so no filter ever sees one; the range tests alone missed a NaN, and the rotation rates and the GPS have none. The campaign measured the difference (FTS-FI-001 Section 7, finding 7). The processor is the only judge of `Validity`, judging all five computed fields last, in order of precedence, so the value and its verdict leave in the same frame (REQ-PROC-007); a field that is not NORMAL holds a defined number, never NaN. Of the three lanes' verdicts the voter passes a majority's through unchanged and, with no majority, degrades the held ones with `min(held, FAILURE_WARNING)`, never raising one (REQ-RED-004). A frame the source flags NEW_VEHICLE restarts every estimate before the gates (REQ-PROC-008).
- **Fault detection → DEGRADED state:** failed sensors don't crash the system. The channel is marked DEGRADED, the fault is logged as a tagged record in the same stream, remaining sensors continue processing, and the channel returns to NOMINAL after M consecutive valid reads.
- **Log format:** raw struct bytes behind a 16-byte self-describing header (magic, version, record sizes, the run mode and the source mode, endianness marker); rotation at record boundaries; format version 3 since 2026-10-15, the 120-byte frame with version 2 as its prefix (`sequence` at 52, `course_deg` at 80, `flags` at 103, a 16-byte tail), with readers accepting 1 to 3 and refusing others by name before anything is built (`main` probes the replay input's header and takes the source mode from it, never from a frame), an older frame read as a prefix with a zero tail, a version-1 frame's validity NOT_JUDGED and former reserved bytes zero; bit-identity is claimed for the records, for the same build on the same platform and within one format version (`docs/design.md` §8 and §9): a session's log and its replay's differ in one header byte, the run mode (REQ-LOG-007).
- **Fixed-rate timing with clock_nanosleep:** absolute-time scheduling (`TIMER_ABSTIME` on Linux; the `nanosleep` fallback for other platforms is one of the two `#if`s in the codebase, the other being the I2C device file in `src/drivers/i2c_bus.cpp`; both sit on the OS boundary), re-phase and count missed cycles on overrun, never burst. Jitter is logged per cycle to a CSV named by the run's prefix (`telemetry_jitter.csv`, `replay_jitter.csv`), not into the telemetry log, so the log stays deterministic.
- **A replay ends at its log and paces on request (REQ-LOG-006, REQ-TIME-004):** `DataSource::has_next()` is true forever for a sensor or the simulator and answered by the replay source from a one-frame look-ahead; the loop asks before every read, so a replay runs to its end by default, `--cycles` caps and never extends, and the `Replay:` line says which ended the run (the padded tail it replaces re-applied the last reading as fresh with `dt` = 0). `--pace` hands each frame's recorded timestamp to a `TimestampPacer` on the same `Clock` seam the scheduler uses, `origin + (t − t0)`, late frames released at once and never skipped; pacing decides when a frame goes out, never what is in it, and the paced log is byte-identical to the unpaced one by test.
- **Kalman filter constants: two measured, two retained, one chosen by replay (REQ-PROC-004, `docs/noise_profile.md`):** the barometric measurement variance is the white part of the barometric altitude noise on a stationary capture (the one-sample Allan deviation squared, immune to the weather's trend) and the initial altitude variance equals it; the process noise describes the vehicle, not a sensor, and stays a documented tuning choice (a Q taken from the accelerometer's own noise would lag a real climb by ten seconds); the GPS variance stays the datasheet figure until a capture with the receiver fixing is analysed; the initial velocity variance, which owns the startup transient, is chosen by replaying the capture through candidates under a rule written before the data. The analysis script and its oracles are built; the capture supplies the values, which land in the `processing` keys of the configuration file and the equal defaults of `ProcessorConfig`.
- **Configuration: one file, validated at startup, injected by value, never global, recorded beside the log (REQ-CFG-001 to REQ-CFG-003):** `config/telemetry_config.yaml` (or `--config`) is the standing configuration and the only source of the values the binary runs with; there is no built-in fallback, and a missing file is refused. `src/config/telemetry_config.cpp` is the one translation unit that knows YAML: it turns the document into typed structs in one pass, checking type and range as it goes (parse, don't validate), with the project's own scalar rules (decimal or `0x` hex, finite numbers, `true`/`false`, non-empty text) and every problem reported together under its dotted key. Values reach modules by constructor, by value (`FaultDetectorConfig`, `ProcessorConfig`, `SimulationNoise`, `AdsbConfig` from the optional block, plain arguments for the rest); no module includes the config header, so a test can hand a module any value. The struct defaults equal the shipped file and are the unit tests' baseline; `ConfigTest.ShippedFileEqualsDefaults` keeps them equal. The file's text is copied beside the log as `<prefix>_config.yaml`; a replay reads it by default, and with `--config` says whether the named file equals the record by content. Flags choose the run and win only on the transports.
- **Dual transport behind one seam:** ZeroMQ for local IPC and UDP for network streaming, mirroring an aircraft-to-ground-station architecture; both built. `Publisher` is `DataSource`'s twin on the output side: the loop holds base pointers and never learns which transport it has, `main` owns the concrete objects, and `--zmq` and `--udp` may be combined. The wire format is the log format: every message and every datagram is a one-record log file (header, tag, frame) assembled by one function in `log_format`, so one Python module describes both and the receiver reads either. Neither publisher blocks (REQ-TRANS-003): the PUB socket has a 100-message high-water mark per subscriber and a bounded linger; the UDP socket is connected at startup (an unroutable or non-unicast destination is refused before the loop), sends with `MSG_DONTWAIT`, and counts every kernel refusal, including the port-unreachable the kernel reports on a later send. The addresses come from the file's `transport` section; `--zmq` and `--udp` enable a transport for one run and override its address. Every frame carries its source's sequence number since format version 3 (REQ-LOG-008); loss and reordering are still measured at the receiver from timestamp gaps, and the voter consumes the number as its staleness check (REQ-RED-006). One message on each transport is not a log record: the nineteen-byte session status (`FTSS`, version 3, mode, state, the source mode, the ADS-B aircraft's address and callsign), RUNNING with the run's mode before frame 0, every second of cycles and at once when the identity changes, after the read and before the frame goes out, ENDED three times after the last frame, so a late joiner learns the mode, a consumer re-takes its track before a new aircraft's first frame and a finished replay never looks like a lost link; readers dispatch on the first four bytes, and the status is never logged.
- **The simulator's scripted flight (REQ-SENS-007):** `--motion demo` hands the generator a `MotionProfile` (keyframes, linear between, held after the end) and the readings are the pipeline's models inverted (`altitude_to_pressure`; an accelerometer vector the filter's `atan2` forms invert exactly; the segment's rates on the gyroscope; fixes integrated from the scripted velocity), with the stationary scenario's seven draws in the same order, so the default is byte-identical; a scenario is a flag, not a key, and the demo is a recorded run of the real binary replayed paced.
- **The display's data path: a bridge and a page, no format change (REQ-DISP-003 to REQ-DISP-005):** `pipeline/bridge.py` reads either transport through the receiver on one thread, hands records to an asyncio loop through `call_soon_threadsafe`, and broadcasts each as JSON by name (every field but latitude and longitude, which never cross; validity and status names beside the numbers) to WebSocket clients, listening on the loopback unless `--listen` says otherwise and greeting each client with `hello` (the stale threshold, the period, the last session status, the counts). The page judges staleness from its own clock at arrival, never from the frame, shows no mode until a status names one, never labels simulated or replayed data LIVE, and shows an ended stream as ended, not stale; its socket and clock are injected, the `Clock` seam in a browser, so its tests use a fake socket and fake timers. The instruments (REQ-DISP-001, -002, -006; `docs/display_spec.md`): one rule, `instrumentState`, decides what each shows, the feed's cause first (the bridge gone, the stream ended, the feed stale, the lag past the threshold the bridge names) and then the worst of its fields' verdicts; a value that cannot be trusted is replaced by a flag naming the instrument, red, or grey for an ended stream, and never struck through; the attitude indicator keeps the symbol fixed and moves the horizon (down for nose up, counterclockwise for a right roll, the bench's signs); the GPS instruments say GS and TRK, the track withheld below a speed; the plot draws the bridge's displacements on a grid, never a map; units convert in one module and the feed stays SI. The lag is elapsed time against elapsed time, never clock against clock, with the bridge's share beside it.
- **The ADS-B source (REQ-SENS-008 to REQ-SENS-011, REQ-CFG-004; design §3 and §10):** `--adsb` builds `AdsbSource`, the fifth source and the first whose sensor is another vehicle. Raw fields take an OpenSky state vector directly (latitude, longitude, the geometric altitude as `gps_altitude_m`, the ground speed, the track as `course_deg`, the fresh flag, and since format version 3 the vertical rate and the pressure altitude, each under a presence bit); the barometer and IMU are NOT_AVAILABLE; no pressure is back-computed from an altitude, because a derived value posing as raw would verify REQ-PROC-001 against its own inverse. The HTTP request runs on `PeriodicWorker`, the project's one thread (a step, the delay it returns, stopped at once by the condition variable's one predicate, joined by its destructor, declared last in its owner), and `poll_once()` publishes one whole `PollReport` into a slot under a mutex, latest wins, an untaken report replaced and counted with its switches carried forward; `read_frame()` takes the slot in one move, so the loop never waits on the network. Sample-and-hold (REQ-SENS-010): `gps_read_ok` is true on the one cycle a new vector (a later position time, or a newly selected aircraft) is first handed over and false on every other, the shape REQ-PROC-006 was written for; the Kalman filter is born from the first fresh reading of either altitude source (REQ-PROC-003), so an ADS-B run has a fused altitude. `AircraftSelector` keeps the nearest descending airborne aircraft to the configured reference point (KSFO) with a 2 km margin and two tolerated misses; every change is recorded with its reason (`initial`, `nearer`, `landed`, `left`, `incomplete`) on the console, in `<prefix>_adsb.csv` beside the log and in the session status at once, and a failed poll is not a miss. `OpenSkyClient` holds the OAuth2 token on the Clock seam, refreshes it 60 s before expiry, repairs one 401 with one refresh and one retry, waits a 429's Retry-After, and counts every failure for the `ADS-B:` exit line. The credentials come from a JSON file outside the repository (`--adsb-credentials`, default under `~/.config/flight_telemetry`, mode 600), never from a key, since the configuration is public and recorded beside every log; the secret travels only in the token request's body, and nothing prints or writes a token, a header or a body. The ten tunables are the optional `adsb` block; the two endpoints are constants, with `--adsb-origin` for the end-to-end test's local stand-in; CI never calls the service, every fixture is synthetic, and the logs of ADS-B sessions never enter the repository (the data license, README). A replay of an ADS-B recording takes the ADS-B channel timeout from the source mode its log's header records (REQ-LOG-007); a version-2 ADS-B log, which records none, replays with the UART timeout unless `--config` names a copy with the ADS-B value (FTS-VR-001 Entry 19). The first frame carrying a newly selected aircraft is flagged NEW_VEHICLE and the processor discards every estimate on it (REQ-PROC-008), so a switch is a new vehicle, not a climb.

## Scope Discipline

This project is built incrementally, topic by topic. When editing files:

- **Only touch what you're asked to touch.** If asked to review `fault_model.md`, don't also rewrite `requirements.md`. Stay in scope.
- **Don't add features, requirements, or code that haven't been discussed.** `docs/requirements.md` defines the scope and `docs/design.md` the architecture. If something isn't in them, it needs a requirement first or it doesn't belong. Open questions live in `docs/design.md` §12; resolve them there before coding against them.
- **Don't restructure the project.** Folder structure and architecture are decided. Improvements to existing files are welcome. Reorganizing everything is not.
- **Review and refine, don't rewrite from scratch.** If a file is 90% good, fix the 10%. Don't delete and start over.
- **Flag issues, don't silently fix them.** If you spot a discrepancy between documents, say so and let the author decide. Don't quietly align them.
- **Cross-document consistency matters.** Requirement IDs, fault IDs, test card numbers, terminology, and technical details should match across all docs. When reviewing, check that references between documents are consistent.
- **Treat existing files as intentional.** They were discussed and decided on; a change needs a reason, not a preference.

## What NOT to Do

- Don't write code without a requirement in `docs/requirements.md`
- Don't skip the traceability matrix update when adding code or tests
- Don't hardcode a tunable — it is a key of `config/telemetry_config.yaml` and a field of its module's config struct, equal by test (REQ-CFG-001); a tunable no requirement names needs the requirement first. The named-constant exception ended with the configuration (2026-10-13); a value a requirement states itself, such as REQ-RED-003's persistence count of three, is a named constant with its rationale in design §12, not a key, so every recorded configuration still replays
- Don't use raw `new`/`delete` — use RAII, std::vector, std::unique_ptr
- Don't skip Google Test for any new C++ module
- Don't mix build artifacts with source (out-of-source build in `build/`)
- Don't go beyond the scope of what's being worked on in the current session
- Don't rewrite files that aren't part of the current task
- Don't add requirements, features, or architecture changes without discussion
