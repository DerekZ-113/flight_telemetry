## 1. Purpose and Scope

This document records the architecture of the Flight Telemetry System and the reasoning behind its design decisions. It exists so that a reviewer can see why the system is shaped this way without reading the source, and so that later decisions are made against a written baseline rather than memory.

It is not an API reference, a build guide, or a tutorial. Interfaces are documented in the headers; build and run instructions are in the README. Where this document and the code disagree, the code is wrong or this document is stale, and either way the disagreement is a defect to record.

---

## 2. Software Level: DAL C

This project assumes Design Assurance Level C under DO-178C. DAL C corresponds to a *major* failure condition: a failure that significantly reduces safety margins or significantly increases crew workload, but from which a safe landing remains possible. A telemetry display that shows wrong altitude or attitude fits that class. It could mislead a pilot and raise workload; on its own it does not cause loss of the aircraft, because certified primary instruments remain.

The practical consequence is in DO-178C Table A-5 (verification of verification process outputs). At DAL C the structural coverage objectives are statement coverage and decision coverage. Modified Condition/Decision Coverage is required only at DAL A. This is the formal basis for the branch coverage thresholds in FTS-TP-001 Section 6 and for MC/DC being out of scope there. The thresholds are not arbitrary targets; they are the DAL C ceiling.

DAL C is an assumption for a development system, not a certification claim. No safety assessment (ARP4761) has been performed, and none is planned. The level was chosen because it is the lowest level at which structural coverage is required, which makes it the lowest level at which the coverage tooling in this project has a reason to exist.

Two further limits apply to every verification claim in this document set. **No independent verification.** Nothing in this project was reviewed or tested by a party independent of the development; the requirements, the code, the tests, and the verification results were all produced and checked within the same development activity. **No tool qualification.** No tool was qualified under DO-330. The coverage figures and the static-analysis result in FTS-VR-001 are taken as reported by gcov, lcov, and cppcheck; a certification project would qualify at least those verification tools, whose output is credited without further checking, at TQL-5 before relying on them.

## 3. DataSource Abstraction

Every frame enters the system through the `DataSource` interface (`src/data_source.h`): one pure virtual method, `read_frame()`, returning a `TelemetryFrame`, and one virtual with a default, `has_next()`, true unless a source overrides it (REQ-LOG-006, 2026-10-14): a sensor and the simulator have no end of stream, a replay does, and the loop asks before every read so that no cycle runs past the end of a log (Section 9). The processing engine holds a reference to the base class and never learns the concrete type. The factory in `main.cpp` is the only place that does.

**Raw-only contract.** A source fills raw sensor fields only: pressure, temperature, accelerometer, gyroscope, GPS position and speed, the `read_ok` flags and, since format version 3, the frame's sequence number and its flags byte, the facts a source states about the frame (Section 7). It leaves every channel status NOMINAL, which from a source means "unjudged" (the detector overwrites all three on every frame, Section 7), every validity byte NOT_JUDGED, and the reserved fields zero. Every computed field (barometric altitude, pitch, roll, fused altitude, vertical speed) and its validity is written by the pipeline. A source that computed its own altitude would be a source and a pipeline at once, and replay could no longer prove that the pipeline reproduces live behavior. One thing a source may say about a status since 0.12.0 (REQ-FAULT-007): a channel it does not provide is NOT_AVAILABLE, a fact about the configuration rather than a judgment about a sensor, which the detector leaves as it is (Section 7).

**Why.** REQ-LOG-004 requires replay to use the same processing pipeline as live mode, differing only in data source. That is only meaningful if the pipeline is a pure function of the raw frames it receives. The abstraction makes the source the single variable.

**Planned implementations.**

| Source | Status | Role |
|---|---|---|
| `SimulatedSource` | Built | Seeded Gaussian noise around a stationary Foster City fix, or, under `--motion`, around a scripted flight (`MotionProfile`, REQ-SENS-007) whose readings are the pipeline's own models inverted; the same seven draws in the same order either way, so the default is byte-identical. Deterministic per seed on a given toolchain. |
| `LiveSensorSource` | Built | BMP280 (or BME280) and MPU6050 over one I2C bus, and a NEO-6M-class GPS receiver on a serial device when `sensors.gps.enabled` names one: one fresh GPS reading per valid fix at the receiver's own 1 Hz, the last fix held between. Without a receiver the GPS fields stay zero and never fresh, and the source reports the channel NOT_AVAILABLE (REQ-FAULT-007), so the detector raises no timeout and no event for a receiver that was never there. Selected by `telemetry --live`. TC-014, TC-018. |
| `LogReplaySource` | Built | Reads the binary log written by the logger, strips computed fields and status, feeds the raw frames back through the same pipeline, and says when the log has ended (`has_next()`, from a one-frame look-ahead). | `AdsbSource` | Built (2026-10-15) | One real aircraft's state from the OpenSky Network REST API, polled on a thread of its own, held between polls, selected with hysteresis (REQ-SENS-008 to REQ-SENS-011; the paragraph below). **Live sensor source.** `LiveSensorSource` (`src/drivers/live_sensor_source.h`) owns the bus and the two chip drivers, in that order, then the receiver's serial port and its driver, and a reference to the monotonic clock. Each `read_frame()` stamps the frame (Section 10), reads the barometer and the IMU, polls the GPS driver when a receiver is configured, and sets every status NOMINAL: raw fields, `read_ok`, and nothing else, the same contract as the simulator, so the detector and the processor cannot tell the two apart. A failed read holds the channel's fields at the last good values and clears that channel's `read_ok`, which is exactly what `FaultInjectingSource::fail_reads` produces, so a pulled wire and the injector make the same frames and the freshness and timeout tests already cover the consequences; before the first good read the fields are the zeros of a value-initialized frame. A barometer whose data registers still hold the reset value (no conversion complete yet) counts as not read. Both drivers are initialized in the constructor and a failure leaves `ok()` false with every failed chip named and the cause; `main` prints that line and exits, because a chip absent or misidentified at startup is a wiring or configuration error, not an in-flight fault (a lazy re-initialization that would let a channel come back belongs with the faults work). The bus and the addresses are `sensors.i2c_device`, `sensors.barometer.address` and `sensors.imu.address` in the configuration file (REQ-CFG-001), and the IMU's sample rate `sensors.imu.sample_rate_hz`; the addresses are provisional (Section 12). The receiver is `sensors.gps.enabled`, `sensors.gps.device` and `sensors.gps.baud_rate`, off in the shipped file until one is wired; a device that does not open at startup is refused by name, as a chip is, while a receiver that stops talking during a run is the detector's to report (FAULT-003). The GPS fields follow the barometer's shape: `gps_read_ok` is true only on the cycle the driver completed a valid fix, once a second, and the fix is held, not fresh, on the cycles between, which is the simulator's 1 Hz schedule and the frames REQ-PROC-006 was written for. The first second after start belongs to the device's backlog: the kernel receives from a USB device only while the port is open, so what the receiver buffered while the port was closed arrives after the flush at open and would parse as current; a fix completing inside that second is counted and discarded, and the first fix delivered is a live one (at most one live epoch is lost to the rule, since a live epoch at 9600 baud is never more than 1.5 s away). The exit line prints the discarded count beside the fixes.

**The I2C bus seam.** The drivers never call the operating system. They call `I2cBus::write_register()` and `I2cBus::read_registers()` (`src/drivers/i2c_bus.h`), one object per bus addressed per transaction, the way the scheduler calls `Clock` and the pipeline calls `DataSource`. `LinuxI2cBus` is the only code that knows what a device file is: it opens `/dev/i2c-1` once, issues `ioctl(I2C_SLAVE, address)` before every transaction because two drivers share the descriptor and alternate addresses every cycle, then writes the register address and reads or writes the bytes. The descriptor is held under RAII, with copying deleted so no two objects can close it. Transactions report false and keep `errno`; nothing throws, because a failed read is an expected event that REQ-FAULT-001 budgets for, not an error. Tests drive the drivers through a fake bus (`tests/unit/fake_i2c_bus.h`) holding a 256-byte register file per address, so each driver's register protocol and arithmetic are proven on a machine with no bus; the fake fails transactions per register, so every branch of a driver's `init()` is reachable. The Linux implementation sits inside the second platform split in the codebase (Section 10); on macOS the class compiles to a stub that reports ENOTSUP, so one source list builds everywhere. A register read is two transactions with a stop between them (write the address, read the bytes); both datasheets permit the stop, and a bus that needed a repeated start would change one function to `ioctl(I2C_RDWR)` with nothing above it.

**The serial port seam.** The GPS receiver talks on its own schedule instead of answering when asked, so its boundary is a byte stream: `SerialPort` (`src/drivers/serial_port.h`) has one method, the bytes waiting on the device, 0 when nothing is, nullopt on an error, and never blocks. `PosixSerialPort` is the one real implementation and the only code that knows what a terminal device is: it opens the path read-only, `O_NOCTTY` (the device must not become the process's controlling terminal, or a 0x03 in the stream could be a signal) and `O_NONBLOCK` (open waits for no modem carrier; read returns what is there), turns the line discipline off with `cfmakeraw` (no line assembly, echo, signal characters or carriage-return translation; eight bits, no parity, one stop bit), sets `CLOCAL | CREAD`, no hardware flow control, a BREAK ignored (a receive-only line gets only noise from one), `VMIN` and `VTIME` zero, one of the six baud rates termios names (a receiver ships at 9600), and flushes the input queue once after the settings take, because a receiver that has been talking to a closed port holds seconds of old sentences and the first fix the pipeline sees must be current. termios is POSIX, so unlike the I2C device file this class has no platform split: the codebase still has exactly two (Section 10), and the port's success path runs in the unit tests on a pseudo-terminal (`posix_openpt`), on the Mac and on the CI runner alike, which the I2C bus's never can. RAII on the descriptor, copying deleted, nothing thrown. With `VMIN` and `VTIME` zero an empty read returns 0 bytes on both kernels, the answer forty-nine cycles in fifty; a read that fails is counted by the driver and shown at exit, and on Linux the one way `EAGAIN` arises with these settings is a second process reading the same device (a `cat` left running on it), which those counts then point at. A terminal the kernel has hung up, a USB receiver unplugged, also reads 0 bytes forever, so each read first asks `poll(2)`, which reports the hang-up on both kernels (measured on a pseudo-terminal whose master closed), and a device that is gone counts as a read error every cycle: the exit line shows a receiver gone as read errors climbing, and one that is merely quiet as a byte count standing still.

**GPS driver.** `NmeaGps` (`src/drivers/nmea_gps.h`) takes a `SerialPort&` as the chip drivers take the bus and is named for the protocol, not the chip (the board is sold as a NEO-6M and described by its vendors as a u-blox 7; nothing here depends on which). Each `poll()`, once per cycle, reads everything waiting in 256-byte chunks up to 4096 bytes, so a receiver at the wrong rate or a USB burst after a stall cannot stretch the cycle, and feeds the bytes to a line assembler: a sentence starts at `$` and ends at a newline, wherever the port cut it (a sentence split across two reads or two cycles completes on the later one), bytes outside a sentence are dropped and counted once per run, a line past 128 bytes without a newline is dropped as overlong. Each complete line must carry its checksum, the XOR of every byte between `$` and `*`, or it is dropped; it is then split into fields and dispatched on the last three letters of its address, whatever the talker (`GPGGA` and `GNGGA` are both GGA). The pure parsing (`src/drivers/nmea.h`, free functions with no state) reads a field in full or not at all, treats an empty field as absent (a receiver without a fix sends `$GPGGA,,,,,,0,00,99.99,,,,,,*48`), and refuses a sentence with a value no receiver can mean (a latitude past 90°, sixty minutes, a fix without a position). A GGA and an RMC carrying the same UTC time field are one epoch, in either order: position, altitude, quality and satellites from the GGA, speed (knots to m/s by 1852/3600) and course from the RMC. The epoch is a fix only when the receiver says so, GGA quality at least 1 and RMC status A; a no-fix epoch is counted and dropped, so the live source's `gps_read_ok` means exactly "a valid fix completed this cycle" and a receiver with no sky view looks to the detector like a silent one (FAULT-003). When two epochs complete in one poll the later is delivered and the earlier counted as skipped, because a reading is applied once and the newest is the one that is current. The driver's counters (sentences, fixes, epochs without a fix, incomplete and skipped epochs, bad checksums, malformed, overlong, resyncs, read errors) are printed by `main` at exit: the detector sees only whether a fix arrived, and the counters are how a silent receiver, one without a fix and one at the wrong baud rate are told apart. The three sizes (128, 256, 4096) are facts about NMEA and the cycle, constants and not keys, like the ZeroMQ high-water mark (Section 12). The oracle for the parser is the u-blox 6 receiver description's printed example sentences with their printed checksums, recomputed independently before the tests were written (TC-018), the way the BMP280 datasheet example is the barometer's.

**Barometer driver.** `Bmp280` (`src/drivers/bmp280.h`) is named for the chip the documents assume and accepts both Bosch identities, 0x58 (BMP280) and 0x60 (BME280), because the BME280's pressure and temperature paths are register-compatible (Section 12); `chip_id()` reports which answered, and anything else is refused with the byte in the message. `init()` reads the 24 calibration bytes at 0x88 (little-endian words, `dig_T1` and `dig_P1` unsigned), then writes `ctrl_meas` = 0x00 (sleep), `config` = 0x00 (0.5 ms standby, IIR filter off), `ctrl_meas` = 0x2F (temperature ×1, pressure ×4, normal mode): sleep first because a `config` written in normal mode may be ignored and a chip left running by a previous process is in normal mode. The settings give about 70 to 83 conversions per second, so a 50 Hz loop never reads one twice, and the IIR filter stays off because the pipeline owns filtering: the Kalman filter is the filter of record and the noise run must measure the sensor, not the chip's smoother. `read()` bursts the six data registers at 0xF7, because the chip shadows them together and byte-wise reads could mix two conversions, assembles two 20-bit fields (high byte first, the opposite order from the calibration), returns nullopt if either is still the reset value 0x80000, and runs the datasheet's integer compensation: `t_fine` from the temperature feeds the pressure, which is why REQ-SENS-002 reads the two together. The compensation is the datasheet's int32 temperature and int64 pressure code transliterated, with the signed left shifts turned into multiplications by the same power of two (shifting a negative value left is undefined behavior in C++17, and the datasheet's own example does it); 64 bits are not optional, because `var1 × var1 × dig_P6` overflows int32 once |var1| exceeds 17,515, which with the example's trimming set is any temperature outside 21.6 to 28.4 °C. The worked example on page 23 of datasheet revision 1.14 is reproduced to the count (TC-012).

**MPU6050 driver.** `Mpu6050` (`src/drivers/mpu6050.h`) checks WHO_AM_I (0x68; the MPU-6500's 0x70 and clone values are refused), then writes five registers: `PWR_MGMT_1` = 0x01 (wake, clock from the X gyroscope's PLL, which the register map recommends over the internal oscillator), `SMPLRT_DIV` for the configured rate (default 100 Hz, twice the loop rate so every poll sees a new sample; one divider serves both sensors, which is REQ-SENS-004), `CONFIG` = 4 (a 20 Hz low-pass filter, below the 25 Hz Nyquist limit of a 50 Hz consumer, 8 ms of delay against a one-second filter time constant), `GYRO_CONFIG` ±250 deg/s and `ACCEL_CONFIG` ±2 g (the finest resolutions; ±2 g is the full scale whose two rails are FAULT-010's limits, `kAccelPositiveRailMps2` and `kAccelNegativeRailMps2`: the extreme codes +32767 and −32768 through the same three constants in the same order as `read()`, so the detector's threshold is what the sensor produces, 19.6194 m/s² one count short of 2 g and −19.62 exactly, and a stated limit cannot drift from it as the 19.62 of Section 12 did). `read()` bursts the fourteen output registers at once, because the chip latches them together and byte-wise reads could mix two samples, assembles each big-endian pair as unsigned and casts to `int16_t` for the sign, and scales by 16384 LSB/g × 9.81 and 131 LSB per deg/s. The chip-to-body axis mapping is the identity, in one place, so a sign the hardware tilt test disagrees with is a one-line change (Section 6). A rate the 8-bit divider cannot produce exactly is refused rather than rounded, which is why REQ-SENS-003's floor is 4 Hz.

**The ADS-B source (REQ-SENS-008 to REQ-SENS-011).** `AdsbSource` (`src/drivers/adsb_source.h`) is the fifth source and the first whose sensor is another vehicle. It presents one aircraft from the OpenSky Network's `states/all` endpoint as the frame's GPS channel: latitude and longitude, the geometric altitude (the aircraft's GNSS height, above the WGS-84 ellipsoid, a different datum from the bench receiver's altitude above mean sea level, about 30 m apart over San Francisco Bay, stated on the display by REQ-DISP-007 and corrected by nothing), the ground speed and the track over ground, all in the SI units the service uses; the barometer and the IMU are NOT_AVAILABLE, because the broadcast carries a pressure altitude but no pressure and no attitude, and a pressure derived from the altitude would be a fabrication posing as a measurement (the pressure altitude and the vertical rate are raw fields of their own since format version 3, each with a presence bit, Section 9). The request runs on the project's one thread (Section 10): `PeriodicWorker` (`src/timing/`) runs a step, waits the delay the step returns, and stops at once when told; the step is `poll_once()`, which fetches through the `HttpClient` seam (`http_client.h`: `get` with a bearer token and `post_form`, the libcurl implementation beside it with its timeouts and no verbose logging, a fake in the tests), parses the response without exceptions (`opensky_json.cpp`, the one translation unit that includes nlohmann/json), selects an aircraft (`AircraftSelector`: airborne, complete and descending, the nearest to the configured reference point, kept while airborne and complete and through a configured number of responses without it, replaced only by a candidate nearer by more than the configured margin, every change recorded with its reason), and publishes one whole poll report into a slot under a mutex, latest wins. `read_frame()` takes the report in one lock and one move, merges the counters, records a switch with the frame's timestamp, and copies the held reading into the GPS fields: `gps_read_ok` is true on the one cycle a new vector (a later position time, or a new aircraft) is first handed over and false on every other, the sample-and-hold REQ-PROC-006 was written for, so the Kalman filter predicts between polls and never re-applies a reading; the first frame carrying a newly selected aircraft is flagged NEW_VEHICLE, on which the processor begins again (REQ-PROC-008, Section 7). The timestamp is the Clock seam's read time, as the live source's. `start()` runs the first poll on the calling thread before the loop, so a refused token refuses the run by name (`main` prints the status and the credentials path, never a body); an unreachable service at startup is counted and tried again. The credentials come from a JSON file outside the repository named by `--adsb-credentials` (REQ-CFG-004), the service's two endpoints are constants of `OpenSkyClient` whose origin `--adsb-origin` replaces for the end-to-end test's local server, and the tunables are the optional `adsb` block of the configuration (the box, the reference point, the interval, the margin, the miss tolerance, the GPS channel's timeout in this mode, which `main` hands to the detector in place of the UART timeout). Every switch is one console line and one row of `<prefix>_adsb.csv` beside the log (`SelectionLog`, the jitter CSV's shape), so a recorded run says which aircraft it tracked, and the loop publishes a session status at once when the identity changes (Section 9). The `ADS-B:` exit line prints the polls by outcome, the token requests, the readings, the switches, the last response's census and the position ages. The data license (read 2026-10-15) allows non-profit research and education, forbids redistribution and operational use, requires de-identified publications and a citation (Section 12): every fixture is synthetic, no capture is committed, the logs of ADS-B sessions stay out of the repository, and the bridge withholds the identity on request for recordings.

**The Python side.** `pipeline/log_reader.py` is the Python twin of `LogReader`: it reads a file through `frame_format`, keeps every complete record and counts a torn tail the way the C++ reader stops on one, refuses an unknown tag, and reads a rotated sequence as one run only when the indices are consecutive, the timestamps increase across the boundary, and the step across it is under a second. A leftover file from an earlier run restarts at 0 and is refused; a leftover from an aborted capture of the same length would join seamlessly (same start, same rotation boundary, same rate), so the reader's summary also prints the frame total and warns when file times are out of order, and the capture procedure clears `logs/` first. It derives a numpy layout from the same struct format string and asserts every field offset against `struct` at import, so the array can never misread the compiler's padding. `analysis/noise_profile.py` consumes it (Section 5, FTS-NP-001). Both are standard-library at import, so the reader's summary runs on the Pi without the venv. `tests/integration/` holds the pytest suite; one simulated session per run, in a temporary directory, serves every test.

**Configuration (REQ-CFG-001, REQ-CFG-002, REQ-CFG-003).** One YAML file, `config/telemetry_config.yaml` or the path given by `--config`, is the standing configuration: 48 keys, every tunable the SRD calls configurable, grouped as their consumers take them (`timing`, `sensors`, `fault`, `processing`, `logging`, `transport`, `simulation`, and `adsb`, the one block a file may omit: ten keys an ADS-B run requires and no other run reads, so a configuration recorded before the block existed replays as recorded). It is a parameter data item in DO-178C's sense (2.5.1): a file with its own structure and limits, verified with the executable rather than patched into it. `main` loads it once at startup through `src/config/telemetry_config.cpp`, the one translation unit that includes yaml-cpp (0.9.0, fetched and pinned like Google Test), which turns the document into typed structs and checks every value's type and range as it goes: parse, don't validate. yaml-cpp is the document parser only; the scalar rules are the project's and the file's header states them (a whole number is decimal digits or `0x` hex, so `010` is refused rather than read as octal; a number is anything `strtod` reads in full that is finite; a switch is exactly `true` or `false`; text is non-empty), because a value two readers read differently has no place in a file validated by name. Every problem the file has is reported in one pass, in the file's order, under its dotted key (`fault.stuck_count: must be at least 2 (got 1)`), which is REQ-CFG-002's "each"; an unknown or duplicate key is a problem too, so a misspelled key cannot silently leave a value at another setting; three rules run between sections (the UART timeout against the GPS period, the IMU rate against the processing rate, the UDP host through `inet_pton` whether or not that transport is enabled). Nothing is built before the file passes, and nothing re-reads it: the loop reads values, never the file, which is why a value is validated at startup and never mid-flight. The values reach their consumers by constructor, by value: the module-owned structs (`FaultDetectorConfig`, `ProcessorConfig`, `SimulationNoise`) and plain arguments for the rest. No module includes the configuration header and no global holds a value, so every test can hand a module any value and the composition root is the one place that knows a file exists. The defaults compiled into those structs equal the shipped file and are the unit tests' baseline, never the binary's fallback: a missing file is refused, and `ConfigTest.ShippedFileEqualsDefaults` fails the build if the two drift apart. Flags choose the run (`--live`, `--replay`, `--cycles`) and enable a transport for one run with its own address (`--zmq`, `--udp`); nothing else on the command line overrides a key. Not keys, each for a reason: the run length (a property of the run), the ZeroMQ high-water mark and linger (Section 12), the record's prefixes and file names (its naming contract), the ISA constants, register maps and chip identities (facts, not tuning), the accelerometer's saturation rails (the driver's full scale through its own scaling; a key stood in for them until 2026-10-14 and drifted, Section 12), and the simulator's base scenario (a scenario, not noise; a scripted scenario is a flag, `--motion`, for the same reason). The configuration a session ran with is recorded beside its log (Section 9).

## 4. Processing Pipeline Order

```
DataSource  →  FaultDetector  →  three TelemetryProcessor lanes  →  Voter  →  Logger / ZeroMQ / UDP / Display
 raw + read_ok     raw + status        raw + computed, three times      one voted frame
```

The fault detector sits before the processor. This is the most important ordering decision in the system.

The detector takes its notion of time from `frame.timestamp_ms`, never from a wall clock. That keeps it a pure function of the frame sequence: a replayed log produces the same faults at the same frames (REQ-LOG-003), and tests advance time by handing in frames with later timestamps. It also fixes the strictness of the timeout comparison. With frames every 20 ms and the last success at t−20, elapsed `> 500` declares the fault 500 ms after the first failed read; `>=` would declare it at 480 ms, which TC-002 treats as a false alarm on a single transient error.

Both filters in `TelemetryProcessor` gate on `ChannelStatus` and on `read_ok`: a DEGRADED channel contributes nothing, and a NOMINAL channel contributes only on a cycle that produced a reading (REQ-PROC-006, Section 5). That gate only protects the filters if status is correct *before* the frame reaches them. A stuck or out-of-range reading that arrives marked NOMINAL enters the Kalman update or the complementary filter and corrupts state that persists across every subsequent frame. Detecting the fault afterward does not undo that. So detection must run first, on the raw frame, and the processor must trust the status it is handed.

The processor itself is a class rather than a free function because both filters carry state between frames. It is passed by non-const reference through the loop and created once, outside it, so the same instance sees every frame in order. Since 2026-10-18 it runs as three identical lanes behind the one detector, and a voter chooses the frame the system emits (REQ-RED-001, Section 13): the detector stays first and single, so a channel's status keeps one writer and a sensor fault is one event, and each lane is given its own copy of the detector's frame.

## 5. Kalman Filter Design

`KalmanFilter1D` (`src/processing/kalman_filter.h`) fuses barometric and GPS altitude (REQ-PROC-003).

**Why 1D, not an extended Kalman filter.** One spatial axis, a linear motion model, and direct measurements of the state mean the standard linear filter is exact. An EKF linearizes a nonlinear model; there is nothing here to linearize. Choosing the simplest filter that is correct keeps every line explainable, which is a project goal in its own right.

**Why two states.** Altitude alone cannot be extrapolated between measurements. Adding vertical velocity gives the predict step something to integrate, and the covariance coupling between the two states lets an altitude-only measurement correct velocity. Vertical speed is therefore estimated without a vertical speed sensor.

**Constant-velocity model and its limits.** The predict step assumes velocity does not change between frames. Process noise Q, built from a single acceleration variance, admits that it does. The model lags under sustained acceleration (rotation, flare, strong thermals). A larger Q shortens the lag at the cost of smoothing. A third state (acceleration) or an IMU-driven predict step would address this and is out of scope.

**Tuning.** Of the filter's five constants (the `processing` keys of the configuration file, the initial altitude variance derived from the barometric one), two are measured by the noise characterization (FTS-NP-001, REQ-PROC-004): the barometric measurement variance, taken as the white part of the barometric altitude noise on a stationary capture (the one-sample Allan deviation squared, which a slow pressure trend cannot inflate the way the plain variance would), and the initial altitude variance, which equals it because the filter is born from one barometric sample. Two are retained as documented tuning choices, because no bench capture can show them: the process noise is the vehicle's unmodelled vertical acceleration (σ_a = 1 m/s²; with a barometric variance near 0.07 m² the filter then sees 90% of a 1 m/s climb after about 1.4 s, where a Q taken from the accelerometer's own electronic noise, as once planned, would take almost 10 s), and the GPS variance stays the receiver's datasheet figure (25 m²) until a capture with the receiver fixing is analysed (the receiver exists since 2026-10-14). The fifth, the initial velocity variance, is the cause of the startup transient of about 0.7 m/s in vertical speed on a stationary board: the prior velocity uncertainty random-walks until the altitude data pins it, a smaller barometric variance does not remove it, and a value of 0.01 (m/s)² would cut the peak to about 0.17 m/s at the cost of seeing a vehicle already climbing at birth about a second later. It is chosen by replaying the capture through candidate values under a rule written before the data (FTS-NP-001 Section 3). Until the capture of 2026-10-13 is analyzed the placeholders stand (3 m² barometric, 25 m² GPS, 1 (m/s)², 1 (m/s²)²) in `config/telemetry_config.yaml` and in the defaults of `ProcessorConfig`, which a test keeps equal; after it the measured values replace them in both places.

**Multi-rate updates (REQ-PROC-006).** The loop runs at 50 Hz; the barometer and IMU are read every cycle and the GPS fixes once per second. `process()` therefore predicts every cycle and applies each sensor only on a cycle in which its channel is NOMINAL *and* its reading is fresh (`read_ok`, Section 7). The filter cannot tell a copy from a new sample: re-applying one reading N times shrinks the covariance as if N sensors had agreed and pins the state to a value that is no longer current. With these constants, a 1 Hz fix applied 50 times would carry the information weight of a 0.7 m sensor (R/50 = 0.5 m²) in place of the 5 m sensor it is; a 500 ms barometer dropout inside the timeout window, re-applied 25 times, would leave the altitude variance at 0.061 m² where prediction alone gives 0.101 m², and during a 2 m/s climb would leave the estimate 0.25 m low with the velocity at 1.875 m/s, where prediction alone is right to the millimeter. Until 2026-10-11 the gate was on status only, and the simulator produced a fresh GPS fix on every frame, so no test could see it (FTS-VR-001 Entry 7). The filter is also constructed on the first cycle with a fresh NOMINAL barometer reading, not on the first frame: a real driver reports `read_ok` false until its first successful transaction, and a filter born from an unmeasured pressure would start 44 km up. Until then the fused fields keep the zero every source leaves in them and read NO_COMPUTED_DATA (REQ-PROC-007, Section 7). From the birth frame they read NORMAL, the start-up transient of about 0.7 m/s in vertical speed included, because an estimate exists and a source contributes; the PFD will show the transient. A source *contributes* when it is NOMINAL now and the filter has taken at least one measurement from it, so the fused fields stay NORMAL on either source alone (FAULT-001's "relies solely on GPS") and read FAILURE_WARNING, at once and for as long as it lasts, when neither contributes: the filter then coasts on prediction, the estimate random-walks, and the ARINC convention is a flag, not a drifting number. The barometric altitude itself is converted only from a fresh NOMINAL reading and held otherwise: 0 and NO_COMPUTED_DATA before the first reading (the ISA formula is not run on a pressure nobody measured, which would read 44 km), the last accepted conversion under FAILURE_WARNING while the barometer is DEGRADED, so the altitude of a reading FAULT-008 discards never reaches the frame.

**Verified behavior.** Fused altitude sigma is 0.23 m against 1.73 m raw barometric over 500 simulated frames with the 1 Hz GPS (0.24 m against 1.65 m before the simulator's GPS went to 1 Hz on 2026-10-11; the seed-42 sequence shifted when GPS noise stopped being drawn on every frame). Two runs are bit-identical. See TC-007 and FTS-VR-001 Entry 7.

## 6. Complementary Filter Design

`ComplementaryFilter` (`src/processing/complementary_filter.h`) estimates pitch and roll (REQ-PROC-002).

**Axis and sign convention.** Right-handed body frame: x forward, y right, z up. Pitch is rotation about y and integrates `gyro_y`; roll is rotation about x and integrates `gyro_x`. Accelerometer tilt uses `atan2(accel_x, sqrt(accel_y² + accel_z²))` for pitch and the y-axis equivalent for roll. **This convention is an assumption.** Whether the mounted MPU6050 agrees in sign cannot be confirmed without hardware. If it does not, the gyro and accelerometer paths fight and the filter converges to garbage; the fix is a sign flip in configuration, and the check is part of hardware week.

**The display's sign rule (2026-10-15).** FTS-DS-001 §2.3 defines `roll_deg` positive as a right roll and `pitch_deg` positive as nose up, the signs TC-014 step 13 expects on the bench (nose up positive, roll right positive). Under the convention above, with y to the right, the code's `atan2(accel_y, …)` reads positive when the right side rises, which is a roll to the left, so the three statements cannot all hold; the first hardware day decides, and a wrong sign is a one-line change in the driver's axis mapping (`mpu6050.cpp`), never in the display. The simulator's scripted flight (Section 3) generates its readings as the inverse of these formulas, so on the simulator a scripted right roll reads positive and draws as a right roll by construction.

**Alpha as a time constant.** The gyro weight alpha (`processing.complementary_alpha`, 0.98 in the shipped file) is meaningless without the sample interval. The accelerometer correction has a time constant of about alpha × dt / (1 − alpha), which at 50 Hz is about one second. A steady gyro bias b settles to an error of alpha × b × dt / (1 − alpha) rather than growing without bound. TC-006 verifies that closed form.

**First-frame seeding.** The first update adopts the accelerometer angles directly. Starting from zero would leave the display wrong for about one time constant after boot, for no benefit.

**DEGRADED behavior (FAULT-006).** When the IMU channel is DEGRADED the filter is not updated, the previous angles are held, and both read FAILURE_WARNING (REQ-PROC-007, Section 7). FAULT-006 asked that the display show a clear failure rather than a frozen reading that looks live; the flag is what gives it that, and the frame keeps a defined number rather than NaN. Before the first seed the angles are 0 and NO_COMPUTED_DATA, an unusable accelerometer at start-up keeping them there; after a reset (next paragraph) they read FAILURE_WARNING until the re-seed, which on a usable recovery frame is the same frame. A stale NOMINAL frame inside the timeout holds the angles and stays NORMAL: staleness is the detector's call. FAULT-007's accelerometer-only fallback for a stuck gyroscope is not implemented; the whole channel is DEGRADED.

**Stale frames (REQ-PROC-006).** A NOMINAL IMU frame whose read failed carries the previous sample. The filter is not updated on such a frame: the angles are held, and the processor remembers the time of the last sample it accepted, so the next fresh frame integrates the gyroscope over the whole gap rather than over one loop period (three stale frames at 50 Hz and a 1 deg/s rate give 0.0784°, not 0.0196°; `ComplementaryTest.GyroIntegratesOverStaleGap`). The same bookkeeping covers a DEGRADED span shorter than the timeout: the first fresh frame after recovery integrates one rate sample over the whole span, which the accelerometer term corrects within about a time constant. Integrating over one period instead would lose the rotation outright. Longer gaps are a different case, next.

**Long gaps re-seed (REQ-PROC-002).** The gyroscope integral rests on the assumption that one rate sample describes the whole interval, and past the communication timeout it does not: one sample multiplied by a ten-second outage, with an uncalibrated MPU6050 offset of several degrees per second in it, would put tens of degrees of false tilt on the display at the moment of recovery. So when the interval since the last accepted IMU sample exceeds the IMU timeout (500 ms, the same `FaultDetectorConfig::i2c_timeout_ms` the detector uses; `main` hands one config object to both, and a `static_assert` keeps the two defaults equal), the processor calls `ComplementaryFilter::reset()` before the update. The filter forgets its seed and keeps its angles, and the update adopts the accelerometer's tilt outright, exactly as the first frame after boot does; an unusable accelerometer on that frame holds the old angles, flagged FAILURE_WARNING, until a usable one arrives. Two asymmetries follow from measuring the gap at the processor rather than the detector. The detector judges a timeout at the failing frame and the processor at the next accepted one, so a dropout the detector tolerated (failed reads from 20 ms to 500 ms) followed by a good read at 520 ms re-seeds although the channel never left NOMINAL. And the processor's gap includes DEGRADED time, so any DEGRADED span longer than the timeout re-seeds on the first NOMINAL frame after recovery whatever the fault was; the recovery frames themselves (M = 5, fresh but still DEGRADED) are not accepted and lengthen the gap. `ComplementaryTest.LongImuGapReseedsFromAccel`, `GapEqualToTimeoutStillIntegrates`, and `ReseedAdoptsTiltedAccel` (TC-006 steps 5 to 7). Decided 2026-10-11 on review of the freshness gate: FTS-VR-001 Entry 7 §7.6 had recorded the re-seed as not planned, and Entry 8 records the change of mind.

**Why not a quaternion EKF.** A full attitude estimator would handle yaw, large angles, and coupled rotations. For a board on a desk and a PFD attitude indicator, pitch and roll from a complementary filter are sufficient and every line is explainable. A production flight system would upgrade; the interface (`pitch_deg()`, `roll_deg()`) would not change.

## 7. Health and Validity

Two vocabularies live in the frame, one per kind of field, each with one judge.

**Channel status (raw fields).** Channel health is a `ChannelStatus` per sensor inside `TelemetryFrame`: NO_DATA until the channel's first successful reading, then NOMINAL or DEGRADED (REQ-FAULT-004, REQ-FAULT-006); NOT_AVAILABLE throughout when the source has no sensor for the channel (REQ-FAULT-007, since 0.12.0). It is what the filters gate on and what a display needs for a raw instrument, and nothing more. Only the fault detector judges it; a source sets NOMINAL, which from a source means "unjudged", and the detector overwrites every status left so on every frame. The one status a source asserts is NOT_AVAILABLE, the fact that it has no sensor for the channel, which the detector leaves as it is: no timeout, no stuck or range check, no event, so an absent sensor is never logged as a failed one, and a replay reproduces the fact from the recorded frames because the replay source's strip leaves it (Section 9). NOMINAL is the encoding's zero so that a value-initialized frame and every frame of a version-1 log read as they did before NO_DATA existed. The first reading makes a channel NOMINAL without an event (a start is not a recovery); a fault on a NO_DATA channel, the communication timeout included, marks it DEGRADED as from NOMINAL, so the detector's promotion rule reads "not yet DEGRADED" rather than "NOMINAL". Before the receiver's first fix the GPS reads NO_DATA for the first two seconds and then DEGRADED; without a receiver configured it reads NOT_AVAILABLE from the first frame (until 0.12.0, NO_DATA and then DEGRADED, with a COMM_TIMEOUT for a receiver that was never there).

Alongside status, each channel carries a `read_ok` flag. This is not health. It says whether the driver obtained a fresh reading this cycle; `false` means the channel's fields are stale from the previous cycle. One failed I2C transaction is normal, so a source reports the fact and the detector decides when staleness has lasted long enough (the I2C timeout, 500 ms by default; longer for the 1 Hz GPS) to be a fault. Keeping the two separate is what lets the transient tolerance of REQ-FAULT-001 live in one place instead of in every driver. The processor honors the same flag: a reading is applied as a measurement only on the cycle it was obtained (REQ-PROC-006, Section 5), so health and freshness gate the filters independently. A NOMINAL channel is often stale (the GPS on 49 of 50 cycles), and a DEGRADED channel can carry fresh readings while it recovers.

**Validity (computed fields, REQ-PROC-007).** Every computed field carries a `Validity` byte in the same frame: NOT_JUDGED (0), NO_COMPUTED_DATA, FAILURE_WARNING, NORMAL, ARINC 429's sign/status vocabulary. The processor is its only judge, as the detector is status's: it owns the filters' state and runs after the detector, so it is the one place that sees both "is there an estimate" and "is its source trusted". Since the voter (Section 13) each lane's processor judges and the voter selects: a majority's verdicts pass through unchanged, and with no majority the voter degrades the held verdicts to FAILURE_WARNING, never raising one. One private function, `judge`, writes all five at the end of `process()`, by one ordered rule per field, the first that applies winning: NO_COMPUTED_DATA while no estimate of the field has ever existed (the Kalman filter unborn, the attitude filter never seeded, no barometer reading ever accepted); FAILURE_WARNING while the channel the field depends on is DEGRADED, or, for the fused fields, while no contributing altitude source is NOMINAL, or for the attitude after a reset until the re-seed; NORMAL otherwise, a stale cycle inside the timeout included. Precedence puts "never existed" first so a flag is never raised over a number nobody measured. Zero means "not judged" and the processor never writes it: a value-initialized frame, a source's raw frame and every frame of a version-1 log read NOT_JUDGED, which no consumer may take for NORMAL, so "the pipeline forgot" is distinguishable from "no data" (`ProcessorValidityTest.EveryEmittedFrameIsJudged` closes REQ-PROC-005). The order is worst first, so `min()` is the worst-wins combiner, which the voter uses to degrade a held verdict under no majority (Section 13). A field that is not NORMAL still holds a defined number, 0 before its first estimate and the held or coasting estimate under FAILURE_WARNING, never NaN: NaN is absorbing in arithmetic and false in every comparison, so a voter or a range check that forgot the flag would fail silently; NaN appears only in the Python reader's `invalid_as_nan` view, where nothing computes on it and a plot should show a gap. Pitch and roll carry the same verdict on every frame (one filter, one seed); two bytes carry one fact, and the uniform one-byte-per-field rule is worth it to a consumer.

**Why the frame and not a sidecar.** Section 12 once deferred the carrier, frame fields or a separate `SystemHealth` record, on two criteria. Both are answered by the validity itself. Health must be inline, because a frame without its validity is the exact artefact this exists to prevent: a display that receives the two separately can pair them wrongly, and on UDP lose one of the two (ARINC 429 carries the sign/status matrix in the same 32-bit word as the data for this reason). And it needs no other rate, because validity is a property of each frame's values. The six tail bytes and four interior bytes the compiler used to pad took the five validity bytes and the reserved fields without a size change (Section 9), so the log, the wire message (121 bytes at version 2) and the Python layout gained names, not bytes. The voter's per-lane state, the sidecar's other motive, was then expected to be the voter topic's own record type, a third tag on the stream; the voter (2026-10-18) needed none: format version 3's `voter_status` carries which lanes are in the vote and whether there was a majority, and the voter's events are new values of `FaultEvent`'s existing channel and type bytes (Section 9), so no tag and no format version was spent. Decided 2026-10-13; the open decision is closed.

**The flags byte and the sequence number (format version 3).** A third kind of field joined the frame with version 3 (2026-10-15): `flags` at offset 103, one byte of named bits (`FrameFlag`), each a fact a source states about the frame, written by the source, recorded by the log, kept by the replay's strip and judged by nobody. Bit 0, NEW_VEHICLE, marks the first frame of a newly presented vehicle (REQ-PROC-008): the ADS-B source sets it on the frame that first carries a newly selected aircraft, and the processor, before its gates, discards every estimate it holds, the Kalman filter, the complementary filter, the IMU's freshness clock, the held barometric altitude and its three "ever" flags, so the frame's own fresh reading births the filter at the new aircraft's altitude with zero velocity by the existing rule and the fused fields leave NORMAL on that frame. The detector ignores the bit: a new vehicle's first reading is a reading, and a channel's health is unchanged by whose reading it is. Bits 1 to 3 are presence bits for optional raw fields: VERTICAL_RATE and PRESSURE_ALTITUDE for the two ADS-B fields of REQ-SENS-008, FIX_QUALITY for the receiver's fix quality and satellite count of REQ-SENS-005. An optional measurement needs a yes or no that no value can carry, since zero is a rate and NaN is silent in arithmetic and false in every comparison, the rule since REQ-PROC-007. The sequence number (REQ-LOG-008, offset 52) is a raw fact of the same kind: a count each source keeps from zero and stamps in `read_frame()` through `DataSource::next_sequence()`, recorded, and reproduced by a replay, which keeps the recorded value; the fault injector passes the wrapped frame's through. The loop does not number frames, because a number the run assigned would not replay.

Fault events (REQ-FAULT-004: timestamp, channel, type, value) are `FaultEvent` structs the detector accumulates and hands out through `take_events()`; `BinaryLogger` persists them as tag-2 records in the same stream (Section 9), tests assert on them, and `main` prints them.

## 8. Determinism

Same-platform replay is bit-exact. `KalmanTest.DeterministicOutput` runs the pipeline twice with the same seed and compares every fused altitude with exact equality. Since 2026-10-18 the three lanes of Section 13 check determinism within a run as well: identical code on identical input, compared bit for bit on every cycle, so a nondeterminism in the processor shows as a disagreement in the run that has it, where replay identity shows it only across two runs; neither sees a defect common to every lane.

Cross-platform determinism is not guaranteed and is not attempted. `std::normal_distribution` is implemented differently in libc++ (macOS) and libstdc++ (Linux, Raspberry Pi), and `std::pow` and `std::atan2` may differ in the last bit between math libraries. A log recorded on the Pi and replayed on the Mac may therefore differ at the least significant digits. This is documented here and in the simulator source, and TC-004 is scoped to same-platform replay. Replacing the standard distribution with a hand-written generator was considered and rejected: the property that matters, live-to-replay equality on the Pi, does not need it.

## 9. Log Format and Replay

The binary log (REQ-LOG-001) is a header followed by tagged records:

```
LogFileHeader (16 bytes): magic "FTLG", format version (3), sizeof(TelemetryFrame),
                          sizeof(FaultEvent), run mode, source mode, endianness marker
{ tag (1 byte), record }   tag 1 = TelemetryFrame (120 bytes), tag 2 = FaultEvent (16 bytes)
```

**Raw struct records.** Both record types are written as their in-memory bytes. That is licensed by `static_assert(std::is_trivially_copyable)` on each: the bytes are the value. It is the simplest correct format for the scope this project claims (Section 8: same platform, same build), and it costs nothing per frame. Field-by-field serialization with fixed widths would be portable across compilers and byte orders and is the right answer for a shipped product; it was considered and deferred as roughly three times the code for a property the project does not claim.

**No unspecified byte (format version 2).** Until version 2 both on-disk structs contained padding the compiler inserted for alignment: `TelemetryFrame` had four bytes before `latitude` and six after `gps_read_ok`, `FaultEvent` two between `type` and `value`, and nothing assigned them. An object declared without an initializer carried stack garbage there, and so did a braced temporary on GCC, and the logger wrote it verbatim; each was found once on 9/9 (the simulator's uninitialized frame on the Mac, the detector's brace-built events on Linux in CI). Version 2 (2026-10-13) names every one of those bytes: `reserved_a` (offset 52) and `reserved_b` (103) in the frame, the five `Validity` fields (98 to 102, Section 7) taking the other tail bytes, and `reserved` (10) in the event, so the structs have no padding at all. The proof is in the headers: `static_assert(sizeof(TelemetryFrame) == 8 + 11*4 + 4 + 2*8 + 5*4 + 3 + 3 + 5 + 1)` with `offsetof` pins, and the same for the event. The sum of the members equals the size only when the compiler inserted nothing (`std::has_unique_object_representations` would read better, but it is false for any type with a floating-point member). Rule, unchanged in spirit: **every struct that reaches the logger is value-initialized (`T x{};`) and then assigned, never brace-built or left default-initialized**, so the reserved fields are zero and the bytes are a function of the fields alone; the sources leave them zero, `strip_to_raw` zeroes them, and the processor does not zero them defensively, because that would mask a source bug. Guards: `SimulatedDataTest.SameSeedSameSequence`, `FaultDetectionTest.EventReservedIsZero`, `FrameLayoutTest.EveryByteIsANamedField`, and the pytest's repacking check (`test_frames_pack_round_trip`). A reserved field is zero until a format version assigns it; version 3 spent both of version 2's (the sequence number and the flags byte), assigned a third in its tail to the voter's status (Section 13) and reserved one more, `reserved_d` (the format version 3 paragraph below, Section 12).

**A new value of an old byte.** `ChannelStatus::NOT_AVAILABLE` (3) joined the status byte on 2026-10-15 (REQ-FAULT-007) with no format bump: no byte moved, a reader of version 2 names the value, and a reader older than the value prints its number, which is what the enumeration's `UNKNOWN` fallback and the Python `.get` were for. A replay reproduces it because the source wrote it into every frame and `strip_to_raw` leaves it, stripping only the statuses the detector judges. The voter's events took the same road on 2026-10-18 (REQ-RED-003, REQ-RED-004, REQ-RED-006): `Channel::VOTER` (3) and the fault types LANE_DISAGREEMENT, LANE_FAULTED, NO_MAJORITY and LANE_OVERRUN (4 to 7) in the event's existing bytes, no byte moved and no version bumped, a reader older than the values printing their numbers. A new enumerator in an existing byte is not a change to the struct; a third record tag, which both readers refuse by name (`log_reader.cpp`, `pipeline/log_reader.py`), would have been one.

**Format version 3 (2026-10-15; REQ-LOG-005, REQ-LOG-007, REQ-LOG-008, REQ-PROC-008).** The frame grew from 104 to 120 bytes with version 2 as a prefix: offsets 0 to 102 keep every version-2 field where it was, the two reserved fields are spent by name, and a 16-byte tail follows, no padding anywhere, the sum-of-members `static_assert` now reading 120. `reserved_a` (52) is `sequence`, a uint32 the source counts from zero (REQ-LOG-008; two bytes would wrap in 22 minutes at 50 Hz, four in 2.7 years); `heading_deg` (80) is `course_deg`, the rename of Section 12 with no byte moved; `reserved_b` (103) is `flags`, the byte of named bits of Section 7. The tail: `gps_vertical_rate_mps` (104, float, positive climbing), `gps_pressure_altitude_m` (108, float, the aircraft's pressure altitude at 1013.25 hPa), `gps_fix_quality` (112, uint8, GGA's quality), `gps_satellites` (113, uint8), then `voter_status` (114, uint16: the decisions the voter of Section 13 states about the frame it produced, VOTED, LANE_1_FAULTED, LANE_2_FAULTED, LANE_3_FAULTED and NO_MAJORITY as bits, zero meaning no voter ran, which every writer put until the voter landed on 2026-10-18; assigned with version 3 so the voter never needed a version 4, and a verdict of the pipeline, so the replay's strip zeroes it as it zeroes validity and the replay's voter recomputes it) and `reserved_d` (116, uint32), zero until a version assigns it, so the next change has room before it needs a bump. `gps_` names the channel a value arrives on, as `gps_altitude_m` does: the ADS-B vector is that channel's reading. The header's 16-bit `reserved` field became two bytes, `run_mode` (10) and `source_mode` (11), the `RunMode` values of `src/run_mode.h` (0, UNKNOWN, for a file older than version 3 and for a replay of one), so the header says how the file was recorded and how its frames were produced, written once (REQ-LOG-007); the header stays 16 bytes, and the frame message, a one-record log file, carries both. `BinaryLogger` and the publishers take the header `main` built; a replay copies its input's `source_mode` into its own header and its status, and `main` hands the detector the ADS-B timeout when the source mode is ADSB, as it does for `--adsb`, reading the header instead of the first frame. The first-frame rule of FTS-VR-001 Entry 18 §18.5 is deleted, not kept as a fallback: the only version-2 ADS-B logs are the live run's under `logs/`, never committed, and a replay of one now says source UNKNOWN and takes the UART timeout, which Entry 19 records. **The prefix rule for readers:** `header_problem` checks the frame size the header's version implies (`frame_size_for`: 104 for versions 1 and 2, 120 for 3) and the event size 16 for all; `LogReader::next` reads that many bytes into a value-initialized frame, so an older frame's bytes land in the first 104 bytes of the version-3 struct, where every one of its fields still lives, and the tail stays zero, the sequence 0, the flags clear; the version-1 sanitizing stays as it was. The Python twin keeps one `Frame` shape for every file: `FRAME` is version 3, `FRAME_V2` serves versions 1 and 2, `parse_record` extends an older frame with zeros, `frame_bytes` keeps each file's own bytes, and `frames_array` packs an older file to the version-3 layout. Identity (REQ-LOG-003) is unchanged, within one version: a version-2 input replayed by this build makes a version-3 log whose raw fields equal the input's, TC-017's version-1 pattern extended. At file level a session's log and its replay's now differ in one header byte, the run mode, by design (the Verified behavior paragraph below). The simulator's seed-42 reference log changed by design, and FTS-VR-001 Entry 19 §19.4 records the new hash with the field-by-field check against the kept version-2 reference: in every frame the first 104 bytes equal the old frame's except at offsets 52 to 55 (the sequence) and 103 (the simulator's FIX_QUALITY bit), and the tail is the simulator's quality 1, 8 satellites and zeros. Rejected: the mode in every frame (a run property repeated fifty times a second); the first-frame rule kept beside the header (two rules for one fact); a sidecar record for the ADS-B fields (a third tag and a second parser for raw readings of the same channel); NaN or a sentinel for an absent raw field (Section 7); a two-byte sequence as Section 12 once sketched; the sequence assigned by the loop (it would not replay).

**Header guards and the readable range (REQ-LOG-005).** The header carries everything a reader needs to refuse a file rather than misread it: magic so a wrong file fails instantly, a version so the format can evolve, both record sizes so a frame-layout change is caught at open time, and an endianness marker for honesty about the platform limit. **Rule: any change to `TelemetryFrame` or `FaultEvent` bumps `kLogFormatVersion` in the same commit.** The `read_ok` flags added on 9/9 were the last free frame change; version 2 is the first bump and version 3 (2026-10-15) the second. A build writes one version (`kLogFormatVersion`, 3) and reads a range (`kOldestReadableLogFormatVersion`, 1, to 3): `header_problem` names the first mismatch ("format version 4; this build reads 1 to 3", "frame size 112 in the header, 120 for version 3 in this build", the size judged per version since the frame grew), its Python twin `check_header` does the same, and `main` probes the replay input's header after the configuration is loaded and before anything is built, so a log the build cannot read stops the run by name instead of feeding zero frames through the pipeline. A version-1 frame has version 2's bytes with zeros, or in a log written before 9/9 stack contents, where version 2 names fields, so one layout serves both: `LogReader::next` sets a version-1 frame's validity to NOT_JUDGED and its reserved fields to zero, and replay recomputes the rest from the raw fields (REQ-LOG-004), which is why a version-1 log replays through this build and its replay log is a version-3 log, said so on the `Replay input:` line; a version-2 frame reads the same way since format version 3, as the first 104 bytes of the 120-byte struct (the format version 3 paragraph above). The Python reader keeps a file's bytes as they are, because its byte-identity tests compare files. A change that keeps the raw bytes in place may extend the readable range this way; one that moves them may not. Bit identity (REQ-LOG-003) is claimed within one version. A replay cannot run past its log since REQ-LOG-006 (the end-of-stream paragraph below); until 2026-10-14 one that did said so at exit, because a replay log padded with repeats of its last frame is a plausible-looking log too.

**Rotation (REQ-LOG-002)** happens before a record that would push the file past the configured limit, never in the middle of one. A torn record makes the tail of a file unreadable and a replay would silently lose a frame. Every file, rotated ones included, starts with its own header, so each is readable alone and `list_log_files` returns them in name order (`prefix_000.bin`, `_001`, ...).

**Fault events** (REQ-FAULT-004) are tag-2 records in the same stream, so an event sits between the frames it occurred at. Replay skips them and reproduces them by re-running the detector; the identity test compares the reproduced events to the logged ones.

**On the wire (REQ-TRANS-001).** The ZeroMQ publisher (`src/transport/zmq_publisher.h`) sends each processed frame as one message laid out as a complete one-record log file: the 16-byte header, the FRAME tag, the 120 frame bytes, 137 bytes in all (121 until format version 3). Pub/sub has no handshake, so a subscriber that joins late gets no once-per-connection header; carrying the header on every message lets any subscriber validate version, record sizes, and byte order from the first message it sees, with the same parser it uses for a log on disk. One layout, one Python module, one constant to bump. The cost is 17 bytes per message, 850 bytes per second at 50 Hz. Fault events are not published: no requirement asks for them on the wire, the frame's status fields already carry channel health, and the tag byte means adding them later is one more message type, not a format change. ZeroMQ calls a message part a "frame"; in this project "frame" is always `TelemetryFrame` and ZeroMQ's unit is a message. The message is assembled by one function, `frame_message` in `log_format`, so the two transports cannot disagree by a byte.

**The session status (REQ-TRANS-004).** One message on each transport is not a log record: nineteen bytes under a magic of their own (`FTSS`, a version byte, 3 since format version 3, a mode byte, a state byte, a source-mode byte, reserved at version 2, three bytes of ICAO address and eight of callsign, zero unless an ADS-B run has an aircraft selected), built by `session_message` in `src/transport/session_message.h` as `frame_message` builds the other, and sent through a second virtual on the `Publisher` seam, `publish_status`, which each transport implements with the same send it uses for frames and counts apart from them. It carries the facts the frames cannot: the run mode, LIVE, SIMULATED, REPLAY or ADSB, which `main` knows because it chose the source; the source mode of REQ-LOG-007, equal to the run mode except in a replay, where `main` reads it from the input's header, so that a page labels a replayed ADS-B recording's datum and identity by what its frames are (REQ-DISP-007); the stream state, RUNNING or ENDED; and in ADS-B mode the identity of the aircraft the frames present (REQ-SENS-009), which the composition root reads from the source through a function handed to the loop, so the loop still never learns the source's type. The loop sends RUNNING before frame 0 and then every second of cycles (`kStatusIntervalMs` over the period, floored, so the interval never exceeds a second), and since 0.12.0 at once when the identity it names changes, after the read and before the frame goes out, so the status still precedes the frame it announces; the periodic one because pub/sub has no handshake and a datagram no connection: a consumer that joins late, a page opened mid-run, learns the mode from the next one rather than from a message sent before it existed. After the last frame of every run it sends ENDED three times (`kEndedRepeats`), because the end is the one message no later message can repair on a lossy channel, and a consumer treats repeats as one. The receiver dispatches on the first four bytes, `FTLG` a frame message and `FTSS` a status, and refuses anything else as before; it keeps the latest status, prints it, and ends on ENDED at once, so a finished publisher no longer looks like a lost link. The status is never logged: the log's header says how it was recorded (REQ-LOG-007) and its end is its end, so the status adds nothing to the log format and the frame message is unchanged by it. The status's own version moved to 2 with the identity (2026-10-15) and to 3 with the source mode (format version 3, the same day); earlier versions are no longer read, since nothing persists a status and a mismatched pair should fail by name. The cadence and the repeat count are facts about the wire, constants beside the high-water mark (Section 12), not keys. Rejected: a second wire message for the identity (`FTID`, 2026-10-15: a second layout, a second parser, a second cadence to get right); a third record tag in the stream (a format bump for a fact the log does not need); a ZeroMQ topic envelope or multipart (no UDP equivalent, and the frame message would stop being a byte-exact log file); a second socket on a second port (two addresses per transport); a mode told to the consumer by its own flag (it says nothing about the end, and it can lie); the end inferred from ZeroMQ's disconnect event (ZeroMQ only, and a crash and a clean exit look alike on UDP). Decided 2026-10-14 with the display's data path.

**The second transport (REQ-TRANS-002).** The UDP publisher (`src/transport/udp_publisher.h`) sends the same 137-byte message (121 until format version 3) as one datagram per frame, which is under every MTU (IPv4 guarantees 576 bytes, Ethernet carries 1500), so a frame is never fragmented and arrives whole or not at all. The socket is *connected* at startup: `connect` on a datagram socket sends nothing, it records the destination and the route so that each `send` needs no address, and it is what makes the kernel deliver this destination's ICMP errors to this socket. It also fixes the source address at startup, so a board that re-addresses its Wi-Fi mid-run fails every send until restart, counted. The destination is one unicast IPv4 address and port (`--udp <ipv4>:<port>` until REQ-CFG-001): `0.0.0.0` and `255.255.255.255` are refused by name; `SO_BROADCAST` is not set, so a kernel that recognizes a directed broadcast refuses it (Linux, at connect) while one that routes it like unicast delivers it (macOS does for the loopback's 127.255.255.255); multicast is not configured. Telemetry downlinks use datagrams for the property a stream cannot give: a frame that could only be delivered after the next one is due is stale, and TCP would hold fresh frames behind a lost old one. Loss and reordering are the receiver's to measure, from the timestamps; the receiver counts a backwards step as out of order. The frame's sequence number (REQ-LOG-008) travels in the frame since format version 3; the receiver still measures loss from timestamps; the voter consumes it as a staleness check since 2026-10-18 (REQ-RED-006, Sections 12 and 13).

**At the display: the bridge (REQ-DISP-005).** `pipeline/bridge.py` is the first consumer after the receiver: it reads either transport through the receiver's own `ByteSource` (ZeroMQ by default, UDP by flag), on one thread that blocks in `FrameReceiver.recv()` as the receiver's main does, and hands each record to an asyncio loop through `call_soon_threadsafe`, the one place the two meet; the loop serves a WebSocket (`websockets` 17.2, the asyncio implementation, no web framework around it) and broadcasts each record to every open connection as one JSON text message. Push, not poll: the server writes the moment a frame arrives, so the page's own arrival time means something, which is what the page judges staleness from, since no frame carries an age (REQ-DISP-003). A frame goes out with every field but the coordinates, and beside the numbers the validity of each computed field and the status of each channel by name, from the same tables the receiver prints from; a session status goes out as a message of its own; every new client is greeted with `hello`, the stale threshold and the period in milliseconds, the last session status if one has arrived, and the receiver's counts, so a page opened mid-run knows the mode at once. The bridge listens on the loopback unless `--listen` names another address, because anything bound to every interface is reachable by every host on the network and the browser is on the same machine. It never forwards latitude or longitude: screenshots and the demo video go public, and the one place every frame passes is the right place for the rule. Since the instruments (2026-10-15) it forwards instead a position relative to the first NOMINAL fresh fix it saw, metres north and east by the spherical approximation (`RelativeOrigin`, R = 6,371,000 m, the twin of the simulator's constant), re-taken after an ENDED and when a timestamp goes backwards, as the page re-takes its lag origin; the origin never leaves the bridge, and a displacement reveals a shape, not a place. Two more display thresholds ride `hello` beside the stale threshold, the ground speed under which the track is withheld (`--track-min-speed`, 1 m/s as shipped) and the lag past which the instruments are removed (`--lag-ms`, 500 ms), so the page has one source of truth for what it judges. It never ends on its own, a quiet source being a quiet source the page shows as STALE, and `broadcast` writes without backpressure, so a slow page accumulates buffered data and never slows the receiver. Decided 2026-10-14 over FastAPI with uvicorn (a web framework and an HTTP stack for one endpoint that serves no HTTP) and over a Node bridge (a second parser of the wire, a second place to drift).

**At the display: the page (REQ-DISP-003, REQ-DISP-004).** `dashboard/` (Vite, React and TypeScript; `useTelemetryFeed` and `App`) is the display's first screen, the feed proven before any instrument is built on it: the mode label (REQ-DISP-004: LIVE, SIM or REPLAY from the session status, and MODE UNKNOWN until one has arrived, so nothing is ever labelled live by default), a state badge (CONNECTING, WAITING, RUNNING, STALE with the age counting, ENDED with the last frame's time, BRIDGE DISCONNECTED with a new socket after a second), the rate over the trailing second, the frame count and the last frame's timestamp, each computed field with its validity by name beside the number (REQ-PROC-007: the number while NORMAL, the number flagged under FAILURE_WARNING, dashes for NO_COMPUTED_DATA, dashes under a PIPELINE annunciator for NOT_JUDGED, because zero means the pipeline never judged it), and each channel's status with whether its reading was fresh. Staleness (REQ-DISP-003) is judged from the page's own clock at the moment a frame arrives, re-judged every 100 ms against the threshold `hello` named (1 s as shipped: fifty frames, and the receiver's own quiet timeout; two periods would flicker on a Wi-Fi hiccup, five seconds would let a pilot read stale numbers); the last numbers stay legible under the mark, the rate reads 0, and an ENDED stream is never stale, since silence after an end is not a fault. The socket constructor and the clock are injected with real defaults, the `Clock` seam's twin in a browser, so the tests (Vitest with jsdom and React Testing Library) drive a fake socket and fake timers and a second of staleness costs no time. The types in `feed.ts` mirror the bridge's JSON field for field; a renamed field fails the build, not a cell. The instruments were built on this feed on 2026-10-15 (the next paragraph); this screen stays below them as the diagnostic view, the one place a flagged or stale value is shown struck through (FTS-DS-001 §8). Chosen over plain JavaScript (the frame contract is the point, and a typed record is the cheapest drift check), over Next.js (a server the bridge already is) and over a static page with no build (no component model for the instruments).

**At the display: the instruments (REQ-DISP-001, REQ-DISP-002, REQ-DISP-006).** `dashboard/src/pfd/` is the Primary Flight Display proper, specified instrument by instrument in FTS-DS-001 (`docs/display_spec.md`): one SVG panel (`Pfd`, an 800 by 520 viewBox scaled to its container, so every coordinate the tests read is a viewBox unit and never a pixel of a window) with a strip at its top that carries the mode label inside the panel, boxed in amber for SIM, REPLAY and MODE UNKNOWN so that no crop of the instruments can lose it, the feed's state with its cause, PIPELINE when a field was never judged, the rate and the lag; an attitude indicator from pitch and roll, in which the symbol is fixed and the horizon moves (`rotate(−roll) translate(0, pitch × 4)`: the translation first, along the ball's own vertical, down for nose up, then the rotation, counterclockwise for a right roll, the bench's signs of Section 6); an altitude tape in feet from the fused altitude and a vertical speed indicator in feet per minute from the fused vertical speed; a ground speed readout in knots and a track indicator from the GPS channel, labelled GS and TRK because a GPS measures speed and course over the ground and this hardware has no pitot and no magnetometer, the track withheld below a speed threshold since a stationary receiver's course is noise; and, beside the panel, a ground track plot of the bridge's displacements on a plain grid with a scale bar, north up, never over a map. What each instrument shows is one function, `instrumentState`: the feed's cause first (the bridge gone, the stream ended, the feed stale, the lag past its threshold), then the most severe verdict among the instrument's fields; a withdrawn value is replaced by a flag naming the instrument, red, or grey for an ended stream, and never struck through, because a struck-through altitude is still an altitude a pilot can read (Section 12). Units convert in one module (`units.ts`, the exact definitions of the foot and the nautical mile) and the feed's state keeps the bridge's SI numbers untouched. The lag (REQ-DISP-006) is the page's elapsed time since a session's first frame minus that frame's elapsed timestamp, two elapsed times from one shared event rather than two clocks with different epochs, with the bridge's `received_at_ms` giving the same measure up to the bridge; a two-second stall of the page's thread read LAG 2.0 s within 4 ms of the thread's return and RUNNING 11 ms later when the queue had drained (FTS-VR-001 Entry 17). The simulator's scripted flight (Section 3, `--motion demo`) is what the demo replays through all of it. Drawn in SVG by React components with the geometry in pure functions (`geometry.ts`), so the tests assert transforms and positions in jsdom and no canvas is involved; a library was rejected because the drawing is the thing to be able to explain.

**The transport seam.** `Publisher` (`src/transport/publisher.h`) is the output-side twin of `DataSource`: one virtual `publish`, one `stats`, a virtual destructor. The loop holds a vector of `Publisher*` and never learns which transports it has; `main` owns the concrete objects, checks each one's `ok()` at startup, and prints each one's summary at exit. `--zmq` and `--udp` may be given together. A third transport is a class and a flag, not a loop change.

**Publishing never blocks the loop (REQ-TRANS-003).** The publisher is a PUB socket, whose send never waits (zmq_socket(3)): when one subscriber's queue reaches the send high-water mark, messages to that subscriber are dropped until it catches up, other subscribers are unaffected, and with no subscriber at all every message is dropped on the spot. The mark is 100 messages, two seconds of frames, so a subscriber that stalls briefly loses nothing and one that falls further behind loses frames rather than slowing the loop; the library's default of 1000 would hold 20 s of stale frames, and a conflating socket (newest message only) would break TC-005's every-frame check. Those drops are silent at the sender, so the publisher counts only what it can see, messages accepted and sends refused, and loss is measured at the receiver from gaps in frame timestamps. A failed bind at startup is reported and `main` exits; a failed send inside the loop is counted and the cycle continues. The socket's linger is 500 ms: context termination at exit waits at most that long for messages the I/O thread has not yet written, instead of the library's default of forever (a stuck subscriber would hang exit) or zero (the last frames of a healthy run could be discarded). cppzmq reports errors by throwing; the publisher translates both failure paths into status and counters at its boundary, and both are reachable from unit tests (an endpoint already bound, a context shut down), so no coverage exclusion hides them. The UDP publisher sends with `MSG_DONTWAIT`, the kernel's form of the same flag: a datagram is queued whole or refused with an error code, never waited on. What the kernel can refuse, and when, differs from ZeroMQ: a full send buffer (EAGAIN; never on loopback, where delivery is synchronous); a port nobody listens on, which the kernel learns from an ICMP unreachable after the fact and reports on a *later* `send` as ECONNREFUSED, one report per ICMP, that datagram not sent; a non-unicast destination (EACCES, at connect on Linux and at the first send on macOS). A receiver whose kernel buffer is full drops on its own side and the sender sees nothing, exactly as a PUB socket at its mark. Every refusal is counted with its errno, never retried, and the cycle continues; the one branch no configuration can reach, `socket()` failing, is reached in a unit test by lowering the process's descriptor limit. One correction to the ZeroMQ figure above for `tcp://`: the kernel's TCP buffers on both ends sit between the two high-water marks and hold minutes of 137-byte frames, so at process level a subscriber that stalls for seconds loses nothing, and the 100-message mark is reached only by a burst (FTS-VR-001 Entry 6 run d) or over `inproc://`, where there are no kernel buffers (TC-010 step 4).

**Replay strips to raw.** `LogReplaySource` zeroes every computed field and resets every `ChannelStatus` to NOMINAL before a frame leaves it, keeping the timestamp, sensor fields, and `read_ok` flags, and since format version 3 the sequence number, the flags byte and the tail's raw fields, facts the source stated, while zeroing `voter_status`, a verdict the replay's voter recomputes (Section 13), and `reserved_d`, as it zeroed the old reserved pair. This is the raw-only contract of Section 3 applied to replay: the detector recomputes status from `read_ok` (observation, kept) and the processor recomputes the rest. A replay that passed the logged results through would let the pipeline be skipped entirely and still "match."

**Verified behavior.** `ReplayTest.ReplayReproducesLiveSession` logs 500 simulated frames with an injected barometer dropout and a stuck IMU across rotated files, replays them through a fresh detector and processor, and finds every processed frame and every fault event bit-identical. At file level, `telemetry` followed by `telemetry --replay logs/telemetry_000.bin` produces `logs/replay_000.bin` whose every record is byte-identical to the original's. Since format version 3 the two headers differ in exactly one byte, the run mode at offset 10, SIMULATED in the session's and REPLAY in the replay's, because the header names the session that wrote each file (REQ-LOG-007): `cmp -l` lists that byte alone, `11 2 3`, and `cmp` from offset 16 is silent. Identity (REQ-LOG-003) is a claim about the processing outputs, which are the records; a replay of a replay differs nowhere. A replay run logs under a different prefix so that session A and session B sit side by side; the replay source opens its input lazily, on the first read, after the logger has opened its output, so the prefixes are what keep the two apart, and `main` refuses to replay a `replay_NNN.bin` from the output directory rather than destroy it.

**The recorded configuration (REQ-CFG-003).** The computed fields are a function of the raw frames, the code, and the configuration. The header pins the code's layout and the frames are the data; the configuration is pinned by a copy of the file's text, verbatim, written beside the log as `<prefix>_config.yaml` once the logger has opened (`logs/telemetry_config.yaml` for a session, `logs/replay_config.yaml` for a replay; one record per directory and prefix, which the Python reader's name rule ignores). `--replay` reads that record by default and the `Configuration:` line says so; `--config` with `--replay` reads the named file instead, and the line says whether its text equals the record (the same configuration under another name), differs (a legitimate run, which is how FTS-NP-001 chooses the initial velocity variance, but not an identity claim), or has no record to compare with. A log with no record and no `--config` is refused naming the expected path. Identity (REQ-LOG-003) is a property of the configuration's text, not of its path.

**End of stream (REQ-LOG-006).** `DataSource::has_next()` says whether `read_frame()` has a frame to give, with a default of true: a sensor and the simulator have no end of stream, so only `LogReplaySource` overrides it, from a one-frame look-ahead that opens files lazily as before, skips an unreadable continuation file as before, and is consumed only by `read_frame()`; `FaultInjectingSource` forwards the question to the source it wraps. The loop asks before every read and stops at the first no, so a replay without `--cycles` runs to its log's end and `--cycles` can cap a replay but never extend it; the `Replay:` line at exit says which ended the run, the log or the cap, by asking once more. Until 2026-10-14 the interface could not say "no more frames": after the last frame `read_frame()` returned that frame again, `exhausted()` reported it, and `main` ran the repeats through the pipeline for the rest of `--cycles`, each one re-applying the last frame's readings as fresh measurements over an interval of zero, REQ-PROC-006's defect in another place, into a log that looked plausible; the exit line was the only sign. `has_next()` was chosen over an `std::optional<TelemetryFrame>` return, the cleaner signature but one that touches every source, every test and the hot path's type, and over a virtual `exhausted()`, which is set only after a failed read and so would let one repeat through. The old fallback stands for a caller that never asks (`ReplayTest.ExhaustedReturnsLastFrame`); the loop no longer relies on it.

## 10. Fixed-Rate Timing

The processing loop runs on a fixed period (REQ-TIME-001; `timing.period_ms`, 20 ms in the shipped file) with per-cycle jitter measured and logged (REQ-TIME-002). Three components: a `Clock` interface at the OS boundary, a `FixedRateScheduler` that owns the deadline arithmetic, and a `JitterLog` that records what each cycle measured.

**Absolute deadlines, not relative sleeps.** Every deadline is `start + n × period`, produced by adding the period to the previous deadline. A loop that slept "period" after its work would run at `period + work + wake latency` per cycle, and that error would add up: 5 ms of work and 0.3 ms of latency drift 5.3 seconds over 1000 cycles. With a fixed grid each cycle's lateness is independent and never accumulates. `TimingTest.DeadlinesAdvanceByExactPeriod` states this in numbers.

**The `Clock` seam.** The scheduler never calls the OS. It calls `Clock::now_ns()` and `Clock::sleep_until_ns()`, the same way the pipeline calls `DataSource::read_frame()` and never a sensor. Tests substitute a fake whose time moves only when the test says so, so a thousand scheduled cycles run in microseconds. This is the injectable clock FTS-TP-001 §2.1 asks for, applied to the one component that needs it; the fault detector reads time from frame timestamps instead (Section 4).

**Linux and macOS sleep primitives.** On Linux, `MonotonicClock::sleep_until_ns` is `clock_nanosleep(CLOCK_MONOTONIC, TIMER_ABSTIME, ...)`, re-issued on `EINTR`. The kernel is given the absolute target, so nothing between reading the clock and sleeping can lengthen the wait. That is the call REQ-TIME-001 names, and it runs on the Raspberry Pi and in CI. macOS has no `clock_nanosleep`; the fallback re-reads the clock and calls `nanosleep` for the remainder until the target is reached. The scheduling logic is identical; only the sleep primitive is weaker, because a preemption between the read and the sleep lengthens that one wait. The `#if defined(__linux__)` inside that function is one of two platform splits in the codebase; the other is the I2C device file in `src/drivers/i2c_bus.cpp` (Section 3). Both sit on an operating-system boundary, and nothing above either differs between platforms. The 1 ms bound of REQ-TIME-003 is claimed only for the Linux path.

**Overrun policy.** If the loop comes back a whole period or more after its deadline, the scheduler skips the deadlines that already passed, reports how many (`missed_cycles`), and keeps the grid. It never fires back-to-back cycles to catch up. A control loop that fell behind and then burst would be worse than one that missed cycles and said so; a telemetry logger gains nothing from the burst either.

**Jitter in a CSV, not the binary log.** Jitter measures this machine on this run. The binary log is the record of the flight and must replay byte-identically (Section 9). Putting non-deterministic timing records into it would make two identical flights produce different logs. So each paced run writes `<prefix>_jitter.csv` beside the log in `logging.directory` (`telemetry_jitter.csv` for a live or simulated run, `replay_jitter.csv` for a paced replay, so a replay can never overwrite a live run's timing evidence), one line per cycle, and prints a min/mean/max/missed summary at exit. The CSV loads straight into numpy for the characterization run on the Pi.

**Replay is unpaced by default, and paced on request (REQ-TIME-004).** Logged frames carry their own timestamps; every time-dependent computation reads those, so pacing adds nothing to the identity check, and a replay without `--pace` runs as fast as the log reads: one that also publishes sends its frames as a burst, and the receiver's gap count shows what a slow subscriber lost. `--pace` is the display's need, a replay at the cadence it was recorded at. `TimestampPacer` (`src/timing/timestamp_pacer.h`) maps each frame's timestamp to a wall-clock deadline, `origin + (t − t0)` with the origin set by the first frame, and sleeps until it through the same `Clock` seam the scheduler uses, so the fake clock tests it in microseconds (TC-020). The grid is the log's, not `n × period`, because a live log's timestamps are real read times with their jitter in them (below). Its overrun policy is the opposite of the scheduler's and has to be: a deadline that has passed is released at once and reported late, never skipped, since a skipped frame would change the output. Pacing decides when a frame goes out and never what is in it, and the proof is a byte comparison, the paced and the unpaced replay logs `cmp` silent (TC-020 step 6). A gap in the log is honoured as recorded; a timestamp behind the previous one is released at once; one that would fall before the clock's epoch is clamped. `run()` takes the scheduler, the pacer and the jitter log as nullable pointers: a live or simulated run has the scheduler, a paced replay the pacer, which waits after the read because its deadline is the frame's own timestamp, an unpaced replay neither; the statements an unpaced run executes, and their order, do not change. Lateness of a whole period or more is reported in `missed_cycles` as whole periods, the scheduler's figure in the pacer's terms, so one `JitterLog` serves both, and the paced `Timing:` line prints min, mean and max lateness and the count late by a period or more (on this Mac's `nanosleep` fallback, 0 / 3.2 / 11.5 ms over 500 frames, none a period late; the Linux figure is CI's and the Pi's). The scheduler was not given a second mode: two grids are two ideas, and this class is the second. No speed multiplier: a rate is a tunable with no requirement. Decided 2026-10-14 with the display's data path.

**Frame timestamps stay with the source.** The simulator stamps 0, 20, 40 ms as before; pacing makes wall time agree with it. The live source stamps the actual read time: `Clock::now_ns()` at the top of `read_frame()`, from the same `MonotonicClock` the scheduler paces on, as milliseconds since the source's first frame (frame 0 is 0, like the simulator), rounded to the nearest millisecond in integer arithmetic. Decided with the live source (Section 12) over the scheduler's deadline grid for three reasons: the source cannot see the deadline, since `read_frame()` takes no arguments and a setter would leak scheduling into every `DataSource`; the frame should say when the data was taken, so an overrun shows as a 40 ms step that the Kalman prediction and the gyroscope integral then account for, and the detector's timeouts are judged on real elapsed time; and the receiver's gap count uses floor division, so jitter under a period never counts and a missed cycle counts as exactly one. The cost is a `dt` of 20 ms plus or minus the jitter instead of exactly 20, which both filters already take from the timestamps. The jitter CSV remains the timing evidence (REQ-TIME-002); the frame carries when the data was taken.

**The receiver's time and the frame's.** A GPS fix carries its own clock: the UTC time field of the GGA and RMC names the measurement epoch, the top of the receiver's second, and the driver uses it to pair the two sentences (Section 3). The frame does not: its timestamp stays the read time of the cycle in which the pair completed, so the log keeps one clock and a replay reproduces the same fix on the same frame. The cost is a latency the frame does not show. At 9600 baud the receiver's six default sentences are about 500 bytes, half a second of transmission, and a 20 ms cycle carries 19.2 of them (230 at 115200), so the epoch is 100 to 500 ms old when the Kalman filter applies its altitude; over USB, where an epoch arrives as one burst, tens of milliseconds. At bench speeds that is nothing; at 1 m/s of climb it is half a metre, inside R_GPS's 5 m. Recorded here and parked in Section 12 with its remedies.

**The project's one thread (REQ-SENS-008).** The ADS-B source's HTTP request takes hundreds of milliseconds and a cycle has twenty, so the request runs on a thread: `PeriodicWorker` (`src/timing/periodic_worker.h`) owns a `std::thread`, a mutex and a condition variable whose only predicate is the stop, runs a step, waits the delay the step returned, and stops at once when told; the destructor stops it, so the object that owns the worker cannot outlive it, and the worker is declared last in its owner so that it is joined while everything it calls is still alive. The step runs with no lock held, and the handoff is one slot under its own mutex, written by the worker in a move and read by the loop in a move, latest wins, so the loop holds a lock for microseconds and never for the network (REQ-TRANS-003's rule applied to an input). Rejected: libcurl's multi interface driven from `read_frame()` (no second thread, but the loop would carry a state machine across cycles and name resolution can still block), and a future per poll (a thread per poll and a destructor that blocks). The cadence is wall-clock, since the service's is; the frame's timestamp and the token's expiry use the Clock seam. The coverage build adds `-fprofile-update=atomic` so gcov's counters stay exact with a second thread.

### 11.2 Display and validity consumers (REQ-DISP)

## 12. Open Design Decisions

- **Health sidecar vs frame fields.** Decided with format version 2 (2026-10-13): validity lives in the frame, one byte per computed field in the bytes the compiler used to pad, and the sidecar is closed (Section 7). FAULT-006 is met by the flag; the voter's per-lane state needed no record of its own (Sections 7 and 13). The format version bumped with it (Section 9).
- **Live source timestamps: scheduled vs actual.** Decided with the live source (2026-10-12): the actual read time from the monotonic clock, as milliseconds since the source's first frame (Section 10). The grid would hide overruns and needs a setter on every `DataSource`; the read time is truthful and self-contained, and the receiver's gap counter tolerates the jitter.
- **Real-time replay.** Decided with the display's data path (2026-10-14): `--pace`, a `TimestampPacer` on the `Clock` seam with the log's own timestamps as its grid, released late and never skipped, the lateness in `replay_jitter.csv` (Section 10, REQ-TIME-004); the paced replay's log is byte-identical to the unpaced one by test (TC-020). Unpaced stays the default and a replay that publishes without `--pace` still does so as a burst. The scheduler was not extended: its grid is `start + n × period`, the pacer's is the log, two ideas in two classes. No speed multiplier, a rate being a tunable with no requirement.
- **Transport tuning in configuration.** Decided on the configuration day (2026-10-13): the ZeroMQ high-water mark (100 messages) and linger (500 ms) stay named constants. REQ-CFG-001 lists transport addresses and ports, and those are keys (`transport.zmq.endpoint`, `transport.udp.host` and `.port`, each with an `enabled` switch), which `--zmq` and `--udp` enable and override for one run. A key without a requirement is scope; the tuning joins the file when a requirement asks for it. The UDP host stays an IPv4 dotted quad (no name resolution).
- **Explicit reserved fields in on-disk structs.** Decided with format version 2 (2026-10-13): `reserved_a` (52) and `reserved_b` (103) in the frame and `reserved` (10) in the event name every byte the compiler used to pad, the sum-of-members `static_assert`s prove no byte is unspecified, and the value-initialization rule now keeps named fields zero rather than invisible ones (Section 9). A reserved field means zero until a format version assigns it; format version 3 (2026-10-15) spent those 32 and 8 bits on the sequence number and the flags byte, assigned 16 of its tail's bits to the voter's status (Section 13) and reserved 32, `reserved_d` (Section 9). The header's own `reserved` field was spent the same day on the two mode bytes (REQ-LOG-007); using it as a wire-only sequence carrier was considered with the UDP transport and rejected (next bullet).
- **Per-message sequence number.** Decided with format version 3 (2026-10-15): `sequence` at offset 52, four bytes, counted by each source from zero through `DataSource::next_sequence()`, recorded by the log and reproduced by a replay, which keeps the recorded value (REQ-LOG-008, Section 9); the receiver's loss accounting stays on timestamps. The voter consumes the number since 2026-10-18 as a staleness check (REQ-RED-006): in the processing loop's one thread a lane cannot lose a frame, only hand back a stale one, so "a lane's loss against its overrun" collapsed to staleness, told by the sequence and the timestamp together (Section 13). Before it: deferred, and the trigger moved (2026-10-14). Loss is measured at the receiver from timestamp gaps, which cannot tell a dropped frame from a scheduler overrun (the sender's jitter CSV can), and a backwards step is counted as out of order. The display was once the consumer expected to need the distinction; it does not: it judges staleness from arrival time (REQ-DISP-003) and shows the receiver's gap count as what it is. The trigger is now the voter, which must tell a lane's loss from its overrun. When the bump comes, the sequence number rides it together with FAULT-003b's fix-quality byte (Section 11.2), so the format changes once; it lives in the frame (`reserved_a`; two bytes were sketched here and four were spent, two wrapping in 22 minutes at 50 Hz), not in the header's 16-bit `reserved` field (the message would no longer be a byte-exact one-record log file, and the field's job is to be zero) and not in a wire-only envelope ahead of the message (two layouts, two parsers). The session status (Section 9) is the one wire-only message, and it carries no sequence.
- **End-of-stream signal on `DataSource`.** Decided with the display's data path (2026-10-14): `bool has_next()` with a default of true, overridden by the replay source from a one-frame look-ahead and forwarded by the injector; the loop asks before every read, a replay runs to its end by default, `--cycles` caps and never extends, and the `Replay:` line says which ended the run (Section 9, REQ-LOG-006). The `std::optional<TelemetryFrame>` return was the cleaner signature and touched every source and test; a virtual `exhausted()` would have let one repeat through. The padded tail it replaces re-applied the last reading as fresh with `dt` = 0, REQ-PROC-006's defect in a new place, which is why `main`'s old exit line (since format version 2) was a symptom, not a fix. `main` still refuses an unreadable input before anything is built (Section 9), so the silent run of FTS-VR-001 Entry 11 §11.8 cannot recur, and `LogReplaySource` still skips an unreadable continuation file in a list silently (`ReplayTest.UnreadableFileIsSkipped`, `HasNextOpensLazilyAndSkipsUnreadable`), which `main`'s single-file `--replay` never reaches.
- **Accelerometer saturation rails.** Decided 2026-10-14: FAULT-010's limits are the two rails of the full scale the driver configures, derived in `mpu6050.h` from the same three constants `read()` scales by (+32767 → 19.6194 m/s², −32768 → −19.62), compared as two signed tests, and the key `fault.accel_limit_mps2` is gone (38 keys). The defect it closes was parked in FTS-VR-001 Entry 8 §8.7 on 2026-10-12: a 16-bit two's-complement range is asymmetric, the positive rail is one count short of 2 g, and a limit stated as 19.62 and compared by magnitude never saw a saturated positive axis, while the one test fed the limit itself rather than a value the driver produces. A magnitude test against the positive rail would be wrong the other way: −32767 converts to exactly minus the positive rail and is a legitimate reading one count inside the negative rail. The alternative kept open, a key for the full-scale range in g from which the driver would write `ACCEL_CONFIG` and both rails would derive, is a REQ-SENS-003 change for the day the range needs to be configurable. A configuration recorded beside an older log carries the key and is refused on replay as unknown; `--config` with a current file is the remedy, as for the `sensors.gps` keys.
- **Gyroscope saturation fault.** No FAULT entry exists for the gyro's full-scale limit (FTS-FM-001 TODO). Still open after the detector landed; FAULT-010 covers the accelerometer only. When it is written, its rails derive from `kGyroLsbPerDps` as the accelerometer's do (previous bullet): at 131 LSB per deg/s the extreme codes convert to +250.13 and −250.14 deg/s, outside a nominal 250, so a limit stated as 250 would trip seventeen codes before the rail rather than never.
- **The Kalman filter is born from the barometer only.** Decided with the ADS-B source (2026-10-15): the filter is born from the first fresh reading of either altitude source, the barometer first when both are fresh on one cycle, with that source's measurement variance as its initial altitude variance (REQ-PROC-003, REQ-PROC-004), and a barometer arriving after a GPS birth is an update at its own variance. The ADS-B source has no barometer, so the altitude tape would have stayed dashed. No recorded log replays differently: the simulator and the scripted flight read the barometer on frame 0, no bench log exists (FTS-VR-001 Entry 14 §14.7), and the one log that would differ is a bench log whose barometer failed its first reads while the receiver already had a fix. Parked here since the validity topic (2026-10-13).
- **GPS stuck detection.** REQ-FAULT-002 says "any channel", but no FAULT entry covers a stuck GPS and a stationary receiver, or a sample-and-hold ADS-B source, legitimately repeats. Either add a FAULT entry with a rule that tolerates legitimate repeats or narrow the requirement.
- **Bus-level fault event (FAULT-004).** Two simultaneous I2C timeouts log two events today. Collapsing them into one needs driver error codes that distinguish a bus fault from two device faults.
- **`TelemetryProcessor` configuration.** Decided on the configuration day (2026-10-13): one `ProcessorConfig` in `processor.h`, the processor being the one consumer of the Kalman variances, alpha and the sea-level reference; the file groups the six keys under `processing`, and the defaults stay for bare construction in tests (Section 3).
- **Where alpha lives.** Decided by the SRD's own words: REQ-CFG-001 names the complementary filter gain, so alpha is `processing.complementary_alpha`, handed to the filter by the processor; the filter keeps its default for bare construction in tests.
- **Accelerometer-only fallback (FAULT-007).** Requires the detector to distinguish a stuck gyroscope from a stuck accelerometer, which the single DEGRADED state cannot express. The sidecar decision it was tied to is closed (Section 7) and the validity byte does not give the distinction either: it would need a fault type on the frame, or a per-sensor status within the IMU channel.
- **Barometer chip identity: BMP280 in the documents, a BME280 board on the bench.** FTS-SRD-001 (the channel definition, REQ-SENS-001, REQ-SENS-002 and its rationale), FTS-FM-001 (FAULT-001, FAULT-004, FAULT-005, FAULT-008, FAULT-009, the degradation matrix), FTS-TP-001 (scope note, TC-001 objective), FTS-TM-001 (SENS-001 and SENS-002 rows), the Section 3 table above, and comments in five source files and two test files all name the BMP280. The board on hand is a HiLetgo GY-BME280. Bosch's BME280 datasheet (BST-BME280-DS001-24 §5.2, Table 17) states the BME280 is downward register compatible with the BMP280, with pressure and temperature control and readout identical, and lists the exceptions: chip ID 0x60 instead of 0x58 (BMP280 datasheet BST-BMP280-DS001-26 §4.3.1), standby codes `110`/`111` meaning 10 ms/20 ms instead of 2 s/4 s, and 20-bit output whenever the IIR filter is on. I2C addressing (0x76/0x77 by SDO) and the temperature and pressure calibration layout at 0x88 are the same; the temperature and pressure compensation code is identical in the two datasheets (BME280 §4.2.3 and BMP280 §3.11.3, compared line by line), so the barometer compensation card's primary oracle, the worked example on page 23 of BMP280 datasheet revision 1.14 (document BST-BMP280-DS001-11, May 2015), serves either chip. That example's measurement table swaps the UT and UP register addresses, a typo a Bosch Sensortec community moderator confirmed on 2022-01-03 and said will not be corrected because the BMP280 is discontinued; the Week 2 map carries the corrected addresses. The BME280's humidity has no requirement and is not read. Cheap boards are sometimes mislabeled, so the chip ID read on the first hardware day decides. If it reads 0x60: name the driver and the compensation card after the BME280, re-check the FAULT-008 and FAULT-009 limits against the BME280 datasheet, reword every BMP280 mention listed above, and bump the SRD version as a wording revision. If it reads 0x58: close this decision and change nothing. Until then the documents keep saying BMP280. **Provisional values (2026-10-12), built before the first hardware day:** the driver is `Bmp280` and accepts both identities, 0x58 and 0x60, reporting which answered through `chip_id()`; `config/telemetry_config.yaml` addresses the barometer at 0x76 and the MPU6050 at 0x68 (`sensors.*.address`, the `SensorConfig` defaults following them by test), and the driver expects WHO_AM_I 0x68 (the board is marked HW-611, usually a BMP280, and the GY-521's AD0 is low). The Pi's `i2cdetect` and `i2cget` readings (TC-014 step 11) either confirm these or land the BME280 rename and any address change (the file and the defaults together) as a small follow-up commit; this bullet stays open until they do.
- **Gyroscope bias handling.** The stationary capture measures the gyro's bias per axis; the complementary filter turns a bias b into a steady tilt of 0.98 × b degrees (Section 6), and the MPU-6050's datasheet allows ±20 deg/s part to part with ±20 deg/s of variation over temperature. Nothing is subtracted yet. Rule (FTS-NP-001 Section 3): if 0.98 × |b| exceeds 1° on either axis, a requirement for subtracting a configured per-axis bias is proposed, conditional on a second capture on another day agreeing within 0.2 deg/s; below 1° the accelerometer term already holds the error. Estimating the bias at startup is not planned (it assumes a still vehicle at boot and needs its own fault mode); the lasting fix is a bias state in the filter.
- **Replay of a rotated session from the CLI.** Still parked (2026-10-14, with the display's data path). `--replay` takes one file: `LogReplaySource` can span rotated files, but `main` hands it a single path, and a replay now ends at that file's end (REQ-LOG-006). A rotated capture is therefore analyzed as one run in Python but replayed one file at a time: the first stationary capture, fifteen minutes at 50 Hz, is about 4.7 MB and rotates at 1 MiB into five files, so `--replay logs/telemetry_000.bin --pace` plays its first 3.3 minutes, enough to prove the feed. A directory or prefix argument to `--replay` is a `main.cpp` argument form, the overwrite refusal extended to it, and tests for each. A session's configuration record is one file per directory and prefix (Section 9), so a rotated session shares one record. Decided for the demo on 2026-10-15: the demo is the simulator's 150 s scripted flight, 7,500 frames in 787,516 bytes, under one rotation, so a single-file `--replay` plays the whole of it; the directory or prefix form stays parked until a demo wants a longer capture.
- **Recorded configuration without a schema version.** Parked 2026-10-14, not built. The configuration recorded beside a log (Section 9, REQ-CFG-003) carries no version the way the log carries a format version, so a replay without `--config` is judged by the record's keys alone: a key the record lacks is `missing`, a key the file no longer has is `unknown`, and the run is refused before anything is built. Adding the three `sensors.gps` keys and removing `fault.accel_limit_mps2`, both on 2026-10-14, each made every record older than the change fail to replay that way; `--config` with a current file is the remedy the accelerometer-rails bullet names, and the replay then says whether the file equals the record by content. Options: a version key in the file with a migration from each earlier version, or a refusal that names the record's version and the current one; or `--config` as the documented path for old logs. A migration keeps the byte-identity claim (Sections 8 and 9), because every key the pipeline reads still holds the value the log was recorded with; a hand-supplied file keeps it only if its surviving keys do. No real recording exists yet (FTS-VR-001 Entry 14 §14.7), so nothing is broken today; decide it before a key change would break the replay of a real capture. The `adsb` block (2026-10-15) was added as optional for this reason: a record without it replays as recorded, and the block's ten keys are required only when it is present and refused by name under `--adsb` when it is not.
- **GPS fix latency.** Decided with the GPS driver (2026-10-14): the frame keeps the cycle's read time and the receiver's UTC time is not stored (Section 10), so a fix is applied up to half a second after its epoch at 9600 baud. Remedies, none taken: a measurement timestamped by the receiver and applied with a delayed-update filter; the receiver's binary UBX protocol at a higher baud rate, which also shortens the half-second; a `--gps-baud` reconfiguration of the receiver at startup. Any of them is its own topic with its own requirement.
- **2D fixes.** GGA's fix quality is 1 for a 2D and a 3D fix alike; only the GSA sentence's fix type separates them, and a 2D fix's altitude is the receiver's assumption, not a measurement. The driver accepts quality 1 and the Kalman filter takes the altitude at R_GPS; the board's capture will show how often a 2D fix precedes the 3D one at a cold start. Since format version 3 (2026-10-15) the frame carries the receiver's fix quality and satellite count (`gps_fix_quality`, `gps_satellites`, REQ-SENS-005), so the detector has the fields to judge; the rule itself, parsing GSA or requiring four satellites as a proxy, stays parked with FAULT-003b (Section 11.2): the receiver's own judgment is the quality field, and a rule the receiver does not share belongs in the detector with a field to judge, not hidden in the source.
- **Flagged values on the instruments (part 2).** The diagnostic page of REQ-DISP-003 keeps a FAILURE_WARNING value and a stale value on screen, struck through and dimmed with the name beside it, because the page exists to show what the feed carries. An instrument is the opposite case: REQ-DISP-001 (Section 11.2) removes a FAILURE_WARNING value under a flag (ALT, VS, ATT), and a stale feed removes every instrument's value under the stale annunciator for the same reason, since a struck-through altitude is still an altitude a pilot can read. The rule enters the SRD with the instruments; the diagnostic page keeps its own rendering. Noted 2026-10-15, and built the same day: REQ-DISP-001 in FTS-SRD-001, the rule in `dashboard/src/pfd/instrumentState.ts`, the flags in FTS-DS-001 §2.1, the diagnostic view's rendering kept below the instruments (§8).
- **Staleness from arrival time cannot see a queue (part 2).** The page judges staleness from its own clock at the moment a message arrives (REQ-DISP-003), so a frame delayed on the way, in the bridge's buffer, in the socket, or in a browser event loop that is slow or throttled, is judged fresh when it finally arrives: arrival time says that a frame came, not that it came on time. Measured 2026-10-15 in the desktop app's browser pane, with the page instrumented by a `MutationObserver` recording each frame's arrival and every change of the badge: the page went STALE 1,012 ms after its last frame, the threshold plus one 100 ms tick, so the binary's exit, the receiver and the bridge add nothing to the mark; over two runs of 544 and 2,500 frames the page's clock stayed within −4 to +33 ms of the frame timestamps with no arrival gap over 60 ms; and with the page hidden for 15.8 s during a run, the 444 frames of that window arrived at the recorded cadence (maximum gap 28 ms, the clock within −2 to +9 ms of the timestamps) and ENDED reached the page 1 ms after the last frame. The pane does not throttle a hidden page the way Chrome throttles a background tab (timers clamped to one second, to a minute after five minutes hidden; message delivery itself continues), so the Chrome case stays untested; the page re-judges staleness on every frame as well as on its ticker, so a throttled ticker only delays the STALE mark once frames have already stopped, and the mark lands within a tick of the tab's return. What no arrival clock can show is a growing delay, and part 2 adds the measurement: the lag, the page's elapsed time since its first frame minus the frame timestamp's elapsed time, constant while the pipeline is on time and growing when frames queue anywhere between the binary and the page, with the bridge's `received_at_ms` beside it to say on which side of the bridge the queue is; a lag past a threshold is a staleness of its own. Built 2026-10-15 as REQ-DISP-006: the lag and its origins in `useTelemetryFeed.ts`, the threshold a bridge flag (`--lag-ms`, 500 ms), the instruments removed under their flags past it; a two-second stall of the page's thread read LAG 2.0 s within 4 ms of the thread's return (FTS-VR-001 Entry 17). Chrome's background tab remains a hand step (TC-025 step 8).
- **The simulator's scripted flight (REQ-SENS-007).** Decided 2026-10-15 with the instruments: `--motion <name>` hands `SimulatedDataGenerator` a `MotionProfile`, a table of keyframes linear in between and held after the last, and the readings are the pipeline's own models inverted: the pressure by `altitude_to_pressure`, the inverse of REQ-PROC-001's relation; an accelerometer vector `g · (sin θ, sin φ, √(1 − sin²θ − sin²φ))` that the complementary filter's two `atan2` forms invert to exactly the scripted angles (a physical gravity vector would give `asin(sin φ · cos θ)` for the roll, 0.01° off at the demo's 2° of pitch in the turn; the exact inverse is the cleaner oracle, FTS-DS-001 §7); the gyroscope the segment's rates, roll about x, pitch about y, the turn rate on z, which the filter ignores and the log keeps; the GPS at a position integrated from the scripted velocity once per generated frame, converted around the stationary scenario's spot by the spherical approximation the bridge also uses. The stationary scenario's seven draws stay in the same order, so the default's bytes are unchanged (the seed-42 hash, FTS-VR-001 Entry 17 §17.4). A scenario is a flag, not a key, by the rule in Section 3. Not taken: a Python-written log (no run would have recorded it, and the demo's claim is a recorded flight replayed) and a bench capture (none exists until the Pi runs). Only `demo` exists; a second profile is another table.
- **`heading_deg` holds the course over ground.** Decided with format version 3 (2026-10-15): renamed `course_deg`, no byte moved, and the simulator's `heading_deg` reading renamed `track_deg` with it. Noted earlier the same day: the frame's field is named for a heading it does not carry (the NMEA RMC course over ground, degrees true), and the display labels it TRK with FTS-DS-001 §4.5 mapping the name. A rename to `course_deg` changes no byte but touches the struct, `frame_format.py`, `feed.ts`, the SRD's channel text, the matrix and the noise analysis; it rides the next struct edit, the fix-quality byte and the sequence number, so the layout and the names change once.
- **The track's speed threshold.** Provisional, 2026-10-15: 1 m/s (the bridge's `--track-min-speed`, FTS-DS-001 §4.5), above a consumer receiver's Doppler noise when stationary and below a walking pace, until the first fix capture measures the stationary course noise; like the chip addresses, the value moves with the measurement, in the flag's default and the specification together.
- **The receiver's out-of-order counter across runs.** Noted 2026-10-15 in the hand run: `pipeline/receiver.py` counts every frame of a restarted run as out of order until its timestamps pass the previous run's (1,488 over two restarts in FTS-VR-001 Entry 17), because its expectation is not reset on a backwards step; the bridge and the page re-take their origins on that step, and the receiver's counter should too. A one-line change with a test, parked with the receiver.
- **The ADS-B pressure altitude and vertical rate.** Decided with format version 3 (2026-10-15): `gps_vertical_rate_mps` (104) and `gps_pressure_altitude_m` (108), each with a presence bit in the flags byte, filled by the ADS-B source from the held vector and held between polls like the other GPS fields (REQ-SENS-008, Section 9); nothing consumes them yet, the vertical rate being Phase B's third measurement. Parked earlier the same day with the ADS-B source. An OpenSky state vector carries the aircraft's pressure altitude (the air data computer's, referenced to 1013.25 hPa) and its vertical rate; the frame's `baro_altitude_m` is REQ-PROC-001's output from a pressure and `vertical_speed_mps` is the Kalman state, computed fields a source may not fill, and no pressure is back-computed from an altitude (a round trip that would verify REQ-PROC-001 against its own inverse). Both ride the next format version with the fix-quality byte, the sequence number and the `heading_deg` rename, one bump; the vertical rate is then the filter's third measurement (the research note's Phase B).
- **The altitude datum.** Noted 2026-10-15: the frame's `gps_altitude_m` names no datum. The bench receiver's GGA altitude is above mean sea level; the aircraft's geometric altitude is its GNSS height above the WGS-84 ellipsoid; over San Francisco Bay the geoid sits about 30 m below the ellipsoid, so an aircraft on the runway reads about −30 m. Phase A maps the value as is and the display names the datum whenever the source mode is ADS-B (REQ-DISP-007, `ft HAE`; since format version 3 for a replay too, REQ-LOG-007); format version 3 spent no field on a datum, the source mode implying it, and a field of its own waits for a source whose datum the mode does not imply; the live run records the figure at touchdown.
- **The data license's obligations.** Read 2026-10-15 (`opensky-network.org/about/terms-of-use`). The license is for non-profit research and education; it forbids making the data available to others, so no captured response is committed, every fixture is synthetic in the real schema, and the logs of ADS-B sessions stay under `logs/` and are expunged at the project's end; it requires a publication to cite *Bringing up OpenSky: A large-scale ADS-B sensor network for research* (Schäfer, Strohmeier, Lenders, Martinovic, Wilhelm, IPSN 2014), which the README does, and to be sent to the network; it requires aircraft identifiers to be de-identified in any publication, which the bridge's `--hide-identity` does at the source for the demo recording; and it reserves "operational" use (a live product, service or automated system) for a written license, so this source runs in attended sessions bounded by `--cycles`, never as a service, and the README says so.
- **A replay's identity.** Parked 2026-10-15. The session status is never logged, so a replay of an ADS-B run shows `REPLAY · ID UNAVAILABLE` (REQ-DISP-007; since format version 3 only when the header's source mode is ADSB, a replayed simulator run having had no identity to lose). The file beside the log records every switch at its frame timestamp, so a replay could re-publish the recorded identities from it at the right frames; `main` in replay mode would read `<prefix>_adsb.csv` when it exists and hand the loop an identity function over it. Not built: the demo's claim is the live aircraft, and the file is the record.
- **The run mode in the log.** Decided with format version 3 (2026-10-15): `run_mode` and `source_mode` in the header's two bytes (REQ-LOG-007, Section 9), the first-frame rule deleted; a replay copies the source mode forward, the detector's GPS timeout follows it, and the session status at version 3 carries it to the page, which labels the datum and the identity by it (REQ-TRANS-004, REQ-DISP-007). Parked earlier the same day with the ADS-B source. A replay of an ADS-B log must give the GPS channel the ADS-B timeout (REQ-FAULT-001), or a 5 s poll interval replays as a timeout the run never had and the replay is not byte-identical; `main` decides from the log's first frame, whose barometer and IMU statuses are NOT_AVAILABLE only when the ADS-B source wrote them (REQ-SENS-011), and says so on the `Replay input:` line. A rule about one source's signature, honest but a heuristic: a mode byte in the log header is the fix, and it rides the next format version with the other parked fields. The page has the same limit, and it matters more than a label: a replay of an ADS-B log is labelled `REPLAY · ID UNAVAILABLE` and its altitude tape reads `ft`, because the page learns the mode from the status and a replay's status says REPLAY, so a replayed approach shows GNSS heights above the ellipsoid under a label that implies height above mean sea level, about 90 ft (27 m at SFO, Entry 18 §18.4) low with nothing to say so, where the live run read `ft HAE`. Parked 2026-10-15 beside the mode in the log: a mode byte in the header lets a replay announce ADS-B and the page label the datum, and format version 3 fixes both at once.
- **The selection measures horizontal distance only.** Found on the live run of 2026-10-15 (FTS-VR-001 Entry 18 §18.5). REQ-SENS-009's rule, the nearest descending aircraft to the reference point, is judged on the ground distance; a descending arrival overflying the field at 3,500 m, 2.4 km from the reference point, displaced the aircraft on short final for 36 s, and the fused altitude followed it up and back. An altitude term, a ceiling on candidates or a slant distance, is the fix; it changes the requirement's words and adds a tunable, so it waits for Phase B rather than entering as a tuning.
- **A switch of aircraft is a discontinuity the filter is not told about.** Decided with format version 3 (2026-10-15): the NEW_VEHICLE bit of the frame's flags byte, set by the ADS-B source on the first frame of a newly selected aircraft, on which the processor discards every estimate and is reborn from the frame's own readings (REQ-PROC-008, Section 7); the detector is not told. Found on the same run. The identity is not in the frame, so the Kalman filter sees a new aircraft's altitude as a step of the old one's and reports vertical speeds of ±150 m/s for a few polls after every switch, pegging the vertical speed indicator until the hold's growing covariance lets the new readings win. The honest fix re-births the filter at a switch, which needs the identity in the frame (format version 3) or a discontinuity flag a source may set; parked with the vertical rate, the measurement that would also make the indicator honest between polls.
- **The voter's persistence count.** Decided 2026-10-18 with the voter: three, `Voter::kLanePersistence`, the default of the voter's constructor parameter, never a key (REQ-RED-003). Why three: the vote masks a wrong lane on every frame, so the count decides only when to stop trusting it, separating a one-cycle upset in a lane's output, which leaves its state intact, from damage to its state, which its filters carry forward; one would discard a healthy lane for good after a single upset and leave a two-lane system for the rest of the run, and a larger count leaves a damaged lane in the vote longer, giving a second fault longer to leave no majority. At 50 Hz a lane is excluded 40 ms after its onset and named in the frame from the next one. The number is chosen, not measured; the fault-injection harness's sweep, building the voter directly with each count over injected faults, is its evidence. Why not a key: every key is required and an unknown key is refused, so a new key would stop every recorded configuration from replaying (REQ-CFG-003, Section 12's schema bullet); an optional key would need a built-in fallback, which REQ-CFG-001 forbids (the `adsb` block escapes only because `--adsb` refuses a file without it, and the voter runs in every mode). A value the requirement states itself is a named constant with its rationale here, as the ZeroMQ high-water mark is. For Sprint 3: a dissimilar lane needs a tolerance, and a tolerance makes agreement non-transitive (a near b and b near c without a near c), so the representative-and-majority rule of Section 13 must be revisited then; the comparison is one function so that the tolerance has one place to go.

## 13. Redundancy and Voting

**What it is (REQ-RED-001).** `RedundantProcessor` (`src/processing/redundant_processor.h`) runs three `TelemetryProcessor` lanes on every frame the detector has checked, one after another in the processing loop's thread, and hands their three outputs to a `Voter` (`src/processing/voter.h`) that chooses the frame the system emits. A lane is one processor: its own Kalman filter, attitude filter, freshness clock, held barometric altitude and "ever" flags, built from the same `ProcessorConfig` and IMU timeout and given its own copy of the checked frame, sharing nothing with another lane (no statics, no references, no clock). The `std::array` of lanes is built element by element from the configuration, never default-constructed: the processor's constructor defaults every argument to the test baseline, which equals the shipped file, so a default-built array would run the wrong tuning with no session test noticing (`RedundantProcessorTest.TuningReachesEveryLane`). All three lanes run on every frame, an excluded one included, so the cycle's work is the same on every cycle and the timing measured is the worst case.

**Why the detector is outside the lanes.** One detector runs ahead of the lanes, as in Section 4: a sensor fault is detected and logged once, the channel status keeps one writer, and the voter never writes a status. A detector in every lane would raise every sensor event three times and, with no majority, would leave the voter choosing a status for a channel the lanes disputed. The lanes still compare statuses (REQ-RED-002), which in this build only an injected fault can make differ; a dissimilar lane would give that comparison its work. The detector's own nondeterminism is caught across runs by replay identity, which compares every event bit for bit (TC-004), not within a run.

**The comparison (REQ-RED-002).** One function, `lanes_agree(a, b)`, compares the thirteen fields a lane writes or carries from the detector: the five computed values, their five validities and the three channel statuses, NOT_AVAILABLE included. Floats are compared as bits, copied into a `uint32_t` with `std::memcpy` (a `reinterpret_cast` read would break strict aliasing, and `std::bit_cast` is C++20), because `==` on floats is not identity: NaN is unequal to itself and −0.0 equals +0.0. A NaN agrees with nothing, so two lanes holding one cannot form a majority: the processor never emits NaN (REQ-PROC-007), so two NaN lanes are two faults. Raw fields, the flags, the tail, the timestamp and the sequence are not compared: the output takes them from the checked frame, so no lane can change them. The comparison has no tolerance, because identical code on identical input has no legitimate difference; it is the one place a dissimilar lane would add one.

**The majority (REQ-RED-002).** A lane is eligible when it is not excluded and its output is for this cycle's frame (the overrun, below). Pairs of eligible lanes are tried in a fixed order, (1, 2), (1, 3), (2, 3); the first pair that agrees names the representative, the lower-numbered of the two, and the majority is every eligible lane that agrees with it. Without NaN, bit equality is an equivalence relation, so there is one majority or none. Whole lanes are compared, not each field on its own: a per-field vote could build a frame no lane produced, pair a value with another lane's validity, and split the two states of one Kalman filter across lanes; the two rules differ only when two lanes are wrong in different fields, a double fault, where the whole-lane rule gives the conservative answer, no majority.

**The output.** The voter starts from the checked frame, so the raw fields, the statuses, the flags and the tail are the detector's, and copies the representative's ten computed fields, the five values and their validities, into it and into a held frame. A majority's verdict passes through unchanged: two lanes agreeing on FAILURE_WARNING give FAILURE_WARNING. In a healthy run the output is therefore exactly what the single processor would have emitted, with the voter's status added: the processor writes only those ten fields (`RedundantProcessorTest.ProcessorWritesOnlyTheFieldsTheVoterCopies` guards it), so the seed-42 log changes in byte 114 of every frame and nowhere else (FTS-VR-001 Entry 20 §20.4).

**No majority (REQ-RED-004).** When no eligible pair agrees, the remaining two lanes disagreeing after an exclusion or every pair of three disagreeing, the frame carries NO_MAJORITY and each computed field the held value with the held validity degraded by `std::min(held, FAILURE_WARNING)`, the worst-wins combiner the worst-first order of `Validity` was chosen for (Section 7): a held NORMAL or FAILURE_WARNING reads FAILURE_WARNING over the held value, "held or coasting" in REQ-PROC-007's words, and a held NO_COMPUTED_DATA stays NO_COMPUTED_DATA over 0, so a flag is never raised over a number nobody voted, and the attitude of the ADS-B source, which has no IMU, keeps its no-source flag (FTS-DS-001 §4.1), never a failure flag. Before the first vote the held frame is zero with every validity NO_COMPUTED_DATA, and a NEW_VEHICLE frame clears it again (REQ-PROC-008) while the exclusions stand, a lane's health being no more the vehicle's than a channel's is. One NO_MAJORITY event marks the start of the condition; the frames' bits say how long it lasted. The statuses stay the detector's, so the raw instruments are unaffected, and the loop goes on.

**Counting and excluding (REQ-RED-003).** Each lane holds a count. On a cycle with a majority, a lane in it resets its count to 0 and a lane outside it, disagreeing or stale, adds one: at 1 the onset event is logged, and at the persistence count, 3, the lane is excluded (LANE_FAULTED) until restart, its LANE_k_FAULTED bit set on every later frame. The bits are taken before the counts move, so the frame on which a lane is excluded still shows the vote it was outside of, and the bit says what `telemetry_frame.h` says it says, that the lane was excluded from the vote. On a cycle with no majority no count moves: nothing says which lane is wrong, and resetting would discard evidence that was good when it was gathered, the detector's own rule ("a frame with no reading proves nothing either way"). It follows that a lane is excluded only when a majority exists that it is outside of; with two lanes left the majority is both, so the vote never falls below two lanes and at most one exclusion bit is ever set. The count is a constructor parameter with `Voter::kLanePersistence` as its default, so the fault-injection harness can sweep it by building the voter directly (Section 12 records why three).

**The overrun (REQ-RED-006).** A computer that overruns hands its voter the output it had, the previous cycle's. In one thread the lanes cannot be late in time, so the overrun is defined by the frame's identity: a lane whose output carries a timestamp or a sequence number other than the checked frame's takes no part in that cycle's vote and, on a majority cycle, counts as outside it, its onset logged as LANE_OVERRUN when staleness is that cycle's reason. Both fields, because the frames of version-1 and version-2 logs all carry sequence 0 and only the timestamp separates them. No clock is read, so the rule replays; a whole cycle that overruns is the scheduler's missed cycle (Section 10), counted in the jitter file and never in the log. Two stale lanes can never outvote a current one, since neither is eligible.

**Events.** The voter's events are `FaultEvent` records with the channel VOTER and the types LANE_DISAGREEMENT, LANE_FAULTED, NO_MAJORITY and LANE_OVERRUN, new values of the existing bytes (Section 9); the value is the lane's number, 1 to 3, exact in a float, or for NO_MAJORITY the number of lanes still in the vote. One event per transition, as the detector logs: a lane's onset, its exclusion, the start of a no-majority run; no clearance event, since an onset without an exclusion is a transient and the bits say how long a no-majority run lasted. `main` logs the frame, then the detector's events, then the voter's, so a healthy run, which raises no voter event, logs exactly the records the single lane logged.

**The lane-fault interface (REQ-RED-005).** `LaneFaultHook` (`src/processing/lane_fault_hook.h`) has two pure virtual functions, `perturb_input(lane, frame)` before a lane runs and `perturb_output(lane, frame)` after it, before the vote; `RedundantProcessor` takes a pointer to one, null by default, the absent idiom of the scheduler and the pacer (Section 10). Lanes are numbered 1 to 3, as in the bits and the events. An altered output is a one-cycle upset that leaves the lane's state intact; an altered input diverges the lane's filters for many cycles, a persistent lane fault from one injection. `main` never builds a hook, which the byte checks show. The fault-injection harness, the next topic, will build the voter directly over hand-made lane outputs to sweep the persistence count and count isolation latency (the first injected frame to the LANE_FAULTED event's timestamp), healthy lanes thrown out (a LANE_FAULTED naming a lane it never altered) and no-majority events, all from the public output.

**Replay.** The replay's strip zeroes the voter's status (Section 9) and the replay runs the same three lanes and the same voter, so a session recorded with the voter replays record for record. A log recorded before the voter, of any version, replays with its status recomputed, VOTED on a healthy run: its records differ from the input's in byte 114 alone, an equality across builds that FTS-VR-001 Entry 20 checks, not an identity claim. A run whose lanes a test altered replays with another status, because the alteration is not in the raw frames; the difference is the diagnosis. A verdict is recomputed rather than copied for the reason the raw-only contract exists (Section 3): a replay proves the pipeline, and a copied verdict would only check the log against itself.

**What it proves, and what it does not.** Three identical lanes on one processor prove the voting mechanism, isolation, latching and the no-majority policy, all driven by injection, and catch nondeterminism within a run, because identical code on identical input has no legitimate difference. They do not survive the Raspberry Pi failing; they cannot catch a sensor fault, since every lane is given the same frame, so a bad reading goes in and three agreeing lanes come out; they cannot catch a defect common to every lane, the same code, compiler and math library; the detector ahead of them is a single point; and in this build only an injected fault can make their statuses differ. A triplex flight computer votes across three processors; this votes across three lanes on one, the mechanism without the hardware. Dissimilar lanes (Sprint 3) would add design diversity and give up bit equality: a tolerance makes agreement non-transitive, so the majority rule above is revisited then (Section 12).
